# luciad

## Summary

STATE OF LUCIAD (now "Octave Alto") FOR SPLATS + POINT CLOUDS, Oct 2026.

Corporate/branding: On 2 Apr 2026 Octave announced Alto 2026.0, renaming LuciadRIA to Alto Browser, LuciadFusion to Alto Server, LuciadCPillar to Alto Universal and LuciadLightspeed to Alto Lightspeed. Octave was spun off from Hexagon: the AGM approved it 24 Apr 2026 and the shares were distributed 28 May 2026. Octave took over Hexagon's SIG business (which held Luciad). The dev portal (dev.luciad.com) still uses the Luciad names, and the 2026.1 portfolio has been released (exact date not found). Because Luciad now belongs to a different company from Leica/Hexagon, check that the user's Luciad licence and access still hold.

Gaussian splats: LuciadRIA supports Gaussian splats starting with 2026.1. LuciadCPillar got them in the same release; neither has them in 2026.0 or 2025.x. LuciadLightspeed and LuciadFusion 2026.1 do not mention splats, so the server cannot tile or serve splats. You have to pre-tile them and host them as static 3D Tiles. Supported input is OGC 3D Tiles whose glTF payloads use KHR_gaussian_splatting (uncompressed) or KHR_gaussian_splatting_compression_spz_2. OGC3DTilesModel also accepts raw PLY or SPZ 2.0 files as tile content, and a single PLY/SPZ can be wrapped in a one-tile in-memory tileset.json with a box bounding volume. Untiled files are limited by memory, so the docs recommend tiled LoD datasets. LoD uses the tileset's geometricError together with TileSet3DLayer.qualityFactor (default 1.0). A global splat budget, RIAMap.performanceHints.maxSplatCount, was added in 2026.1. The recommended profiles are Low (1M splats, qualityFactor 0.5, resolutionScale 0.5, opacityCutoff 0.06) for phones up to Ultra (6M splats, qualityFactor 1.0, cutoff 0, highPrecisionColors) for gaming GPUs. GaussianSplatsStyle has colorExpression, visibilityExpression, scaleExpression, displacementExpression, density, enableDepth (default true; needed for occluding other layers, measuring and precise navigation), highPrecisionColors, opacityCutoff and resolutionScale (0.5–1). The Luciad docs do not say whether spherical-harmonic (view-dependent) colour is rendered, and no SH option is exposed. Treat SH as unknown and test it. Limitations: 3D Tiles 1.1 is only partly supported. Multiple contents per tile and multi-node glTF tiles are not supported. Declarative styling in tileset.json is ignored. CMPT cannot hold PNTS.

Point clouds: LuciadRIA reads 3D Tiles 1.0 PNTS (Draco OK), 3D Tiles 1.1 GLB/glTF point clouds, and HSPC (Hexagon Smart Point Cloud, version 22 or older, plus .pack files). Styling uses PointCloudStyle: color/visibility/scale/displacement expressions, pointSize in PIXEL, WORLD or ADAPTIVE_WORLD mode (default 3 px), gapFill, density and normalOriented. A global point budget, maxPointCount, was added in 2026.1, with recommended profiles of 5M/10M/15M/25M. LuciadRIA cannot read LAS/LAZ directly. LuciadFusion reads LAS, LAZ and E57 and turns them into 3D Tiles 1.0 or 1.1, with Draco optional. Since 2026.1 it also accepts non-georeferenced LAS/LAZ, to which it gives a cartesian reference. That fits a BLK2GO scan with no GNSS. Docs say BLK2GO/BLK360 data can come as HSPC, but HSPC is proprietary, so it does not suit a pipeline meant to be open.

Compositing, clipping, navigation: Splats and LiDAR load as two separate TileSet3DLayers on the same map. Each can be shown or hidden on its own, and enableDepth gives correct depth between them. ExpressionFactory.isInside(orientedBox) inside a visibilityExpression can clip both layer types to an oriented box. The samples also include cross-section and magnifier tools. Built-in navigation limits are weak: MapNavigator.constraints.above (terrain/mesh/minAltitude) works only on geocentric 3D maps, is always off on 3D cartesian maps, and does not apply when code drives the camera directly, which is how first-person controllers work. limitBounds and scale work only in 2D. The first-person controller is sample code, not part of the API. Since 2026.0, synchronous pick no longer hits 3D Tiles, so ground queries must use async pick. Conclusion: walk-mode limits (no going below ground, no passing through set surfaces) need custom code in Luciad just as in three.js. Ship them as a viewer-independent data file (a ground heightfield from the LiDAR plus no-go volumes).

Georeferencing: In LuciadRIA, a tileset with region bounding volumes or a root ECEF transform is treated as georeferenced (EPSG:4978). A tileset using a box with no root transform is treated as LUCIAD:XYZ, a cartesian frame in metres with X east, Y north, Z up. That data is placed with TileSet3DLayer.transformation (an Affine3DTransformation, either a 4x4 row-major matrix or createTransformationFromGeoLocation(point, {azimuth, anchorPoint})), or interactively with the Geolocate sample's GeoLocateController. The docs say it is not warped for earth curvature, which is fine at 10x10 m. You can also make a pure cartesian 3D map (RIAMap with the LUCIAD:XYZ reference), but then lookFrom and the above-terrain constraint do not work. Applying the same transformation to both layers keeps them aligned.

Browser/delivery: Since 2026.0 LuciadRIA runs only on WebGPU. WebGL and the software map are gone, it needs HTTPS (or localhost), and there is no CPU fallback. WebGPU needs Chrome 121+ on Android 12+ with Qualcomm/ARM GPUs, Safari on iOS/macOS 26, or Firefox 141+ on Windows / 145+ on macOS. Older phones are explicitly flagged as unsupported or broken. LuciadRIA is commercial and comes only inside the Luciad product distribution. Production use needs a separate deployment ("end user") licence file; the docs do not give its terms (domains, users, expiry), so ask Octave. The Essential tier already includes point clouds and 3D Tiles; which tier includes splats is not stated.

Hexagon products: hxdr.com now redirects to "Hexagon GeoCloud" (Reality Cloud Studio), which offers browser point-cloud viewing and sharing with stakeholders outside the organisation. None of the GeoCloud, Cyclone 3DR or REGISTER 360 PLUS pages fetched mention Gaussian splats. No confirmed Hexagon product shows BLK2GO LiDAR and splats together in a browser. Confidence is low because the WebSearch budget ran out partway through.

Same data for every viewer: Produce two separate 3D Tiles tilesets in one local metric ENU frame. (a) Splats: tileset.json plus single-node GLB tiles with KHR_gaussian_splatting and KHR_gaussian_splatting_compression_spz_2. The SPZ stream must be format v2 (gzip) in the LUF axis convention, not the current SPZ v4 (ZSTD). KHR_gaussian_splatting base was ratified (PR merged 27 Jan 2026). The SPZ_2 extension is still a draft PR, though CesiumJS (1.135+) and Luciad 2026.1 both implement it. (b) LiDAR: 3D Tiles PNTS (widest support) or glTF points, with no CMPT and no multiple contents. Use a box bounding volume with no root transform for the local three.js viewer and the Luciad LUCIAD:XYZ path. Add a second, thin tileset.json variant with a root ENU-to-ECEF transform for Cesium or a georeferenced Luciad globe; both variants can point at the same tile files. Keep a flat .spz/.ply export for Spark, PlayCanvas or SuperSplat. Make the primary public viewer a WebGL2 three.js/Spark app so older phones still work, and keep Luciad as an optional extra.

## Recommendations

- **Make one canonical output in a local metric ENU frame (metres, Z up, origin at a surveyed ground point on the loop, X/Y from the BLK2GO SLAM frame). Publish two separate 3D Tiles tilesets: splats/tileset.json and lidar/tileset.json. Do not use multiple contents per tile or CMPT.** — LuciadRIA does not support multiple contents or multi-node glTF per tile. A box bounding volume with no root transform loads in Luciad as LUCIAD:XYZ, matching ENU axes exactly, and loads directly in a three.js/3DTilesRendererJS viewer. Two layers can be toggled and composited independently in every viewer. _Alternatives:_ A single combined tileset is not possible in Luciad. Running LuciadFusion as the LiDAR tiler (2026.1 accepts non-georeferenced LAS/LAZ) works, but ties the pipeline to a commercial server.
- **Splat tiles: write single-node GLBs with KHR_gaussian_splatting + KHR_gaussian_splatting_compression_spz_2. The SPZ stream must be format v2 (gzip) in the LUF axis convention, with SH degree ≤3; produce SH0 and SH3 variants for testing. Add simplified parent LoD tiles with correct geometricError. Also export one flat .spz (v2) / .ply of the whole scene.** — This is the only splat encoding that Luciad 2026.1, CesiumJS 1.135+ and three.js + 3DTilesRendererJS/Spark all handle. The SPZ library now defaults to format v4 (ZSTD), which Luciad's 'SPZ 2.0' reader will likely reject. Luciad can show a 10x10 m test scene from a single file wrapped in a one-tile tileset (within the 1–6M splat budgets). Tropical-forest scenes will need real LoD tiling. _Alternatives:_ Uncompressed KHR_gaussian_splatting GLBs are also accepted by Luciad and are useful for debugging, at roughly 10x the size. Raw PLY/SPZ in a one-tile tileset is the quickest Luciad smoke test.
- **LiDAR tiles: use 3D Tiles 1.0 PNTS (or 1.1 glTF POINTS) carrying RGB/intensity/classification, with optional Draco (or meshopt for glTF), from an open LAS/LAZ tiler. Do not use HSPC as the shared format.** — LuciadRIA reads PNTS and glTF point clouds with full expression styling. PNTS has the widest viewer support. HSPC is proprietary and viewer-specific. _Alternatives:_ LuciadFusion 2026.1 can create 3D Tiles 1.0/1.1 from non-georeferenced LAS/LAZ if a Fusion licence is available.
- **Write two thin tileset.json variants per dataset that share the same tile files: (a) local, with a box and no root transform; (b) georeferenced, with a root ENU→ECEF 4x4 transform at an approximate site lon/lat/height and heading. In Luciad, either load (b), or load (a) and apply one createTransformationFromGeoLocation(point, {azimuth}) to both layers.** — Luciad and Cesium place data on the globe via the root transform or region. three.js prefers the local frame. Only the root JSON changes, and putting the same transform on both layers guarantees they stay aligned. _Alternatives:_ A pure LUCIAD:XYZ cartesian RIAMap with no globe at all. This is simpler, but loses lookFrom and the MapNavigator 'above' constraint.
- **Ship navigation limits as data that does not depend on any viewer: a ground heightfield/DTM grid from the LiDAR ground class plus no-go volumes (oriented boxes/polygons) in the same ENU frame. Build a custom first-person/walk controller in each viewer that reads them.** — Luciad's built-in limits ('above' terrain/mesh) work only on geocentric maps and are bypassed by direct camera control. Synchronous pick no longer hits 3D Tiles, so ground clamping needs custom logic in Luciad and three.js anyway. Luciad visibilityExpression isInside(orientedBox) can reuse the same boxes to clip floaters or make cut-aways. _Alternatives:_ Hand Luciad an invisible ground mesh layer with isPartOfTerrain=true and use the 'above' mesh constraint for orbit-style navigation only.
- **Make the primary public viewer a WebGL2 three.js app (Spark for splats plus a 3D Tiles loader). Keep LuciadRIA 2026.1+ as an optional second client.** — LuciadRIA 2026.x needs WebGPU, HTTPS and recent devices (iOS 26+, Android 12+ with a Qualcomm/ARM GPU, Chrome 121+), with no fallback. It also needs a commercial deployment licence from Octave, now a separate company from Hexagon. This matches the user's own requirement that Luciad not be a hard dependency. _Alternatives:_ CesiumJS (Apache-2.0, WebGL2) reads the same 3D Tiles splats and point clouds and is a good reference or cross-check viewer.
- **Run a cross-viewer conformance check early. Put an asymmetric marker object (e.g. an L-shaped board) in the scene, then load the same tilesets in Luciad, CesiumJS and the three.js viewer and compare axes, handedness and scale against the LiDAR.** — Bugs are likely in glTF Y-up versus 3D Tiles Z-up handling, SPZ LUF/RUB axis conversion, and draft-extension details (the SPZ_2 PR is still open), and these can silently mirror or rotate splats in one viewer. _Alternatives:_ Validate tiles with 3d-tiles-validator / glTF-Validator. Their support for the splat extensions is not verified.

## risks

- The KHR_gaussian_splatting_compression_spz_2 extension is still an unratified draft (open PR #2531). Luciad 2026.1 and CesiumJS implement it, but later spec changes (SH index mapping, axis semantics, SPZ version handling) could break compatibility between viewers.
- SPZ version mismatch: SPZ v4 (ZSTD) from the current Niantic library will likely not load in Luciad, which expects SPZ 2.0. Many splat tools write SPZ v3/v4 by default.
- Luciad's documentation says nothing about rendering spherical harmonics. Splats trained with SH3 may lose view-dependent effects in Luciad and look different from Spark or CesiumJS.
- LuciadRIA 2026.x needs WebGPU, so many phones (older iOS than 26, Android below 12 or with non-Qualcomm/ARM GPUs, Linux) cannot run it, and there is no fallback. A Luciad-only delivery would fail the 'phones' requirement.
- Licensing and organisation: Luciad now belongs to Octave, independent of Hexagon since 28 May 2026. The user's access as a Hexagon (Leica-side) employee, and the right to deploy a public app for outside viewers, may need a new agreement. Deployment licence terms are not public.
- Luciad does not support multi-node glTF or multiple contents per tile. Some splat tilers and generic glTF exporters write multi-node GLBs, which Luciad would reject.
- Axis conventions (glTF Y-up versus 3D Tiles Z-up, SPZ RUB/LUF, LAS Z-up, SLAM frame) can silently mirror or rotate splats against the LiDAR in one viewer but not another.
- No built-in Luciad walk/collision mode: the 'above' constraint is off in cartesian maps and bypassed by direct camera control, so navigation limits need custom code in Luciad too.

## FACT-CHECK: recommendation assessment

The core architecture holds. It calls for: two separate 3D Tiles tilesets (splats and LiDAR) in one local metric ENU frame; a Box with no root transform, so Luciad treats them as LUCIAD:XYZ; a thin georeferenced tileset.json variant; single-node GLBs with no CMPT or multiple contents; PNTS or glTF points rather than HSPC; walk and boundary limits shipped as data that does not depend on any viewer; and Luciad kept optional because it is WebGPU-only and needs a commercial deployment licence from Octave. Every Luciad-specific fact behind these points checked out against dev.luciad.com.

Changes I would make:

1. **SPZ version.** Replace 'SPZ must be format v2' with 'gzip SPZ, format v3 (or v2), LUF, never v4'. 'spz_2' and Luciad's 'SPZ 2.0' mean the Niantic library release v2.0.0. LuciadRIA bundles that release, and it writes format v3 and reads formats 1–3.
   - Option A: pin spz v2.1.0, which writes v3 natively and has Python bindings. You build them from source on Windows; the PyPI package named 'spz' is an unrelated Rust crate with no Windows wheels.
   - Option B: use spz v3.0.0 with PackOptions.version=3 (or 2).
   - Encode both v2 and v3 in the first Luciad smoke test.

2. **three.js viewer.** Fix 'three.js + Spark + 3D Tiles loader'. Spark 2.x does not read 3D Tiles. Its streaming LoD uses its own .RAD format via build-lod, with default budgets of 1M splats on Android, 1.5M on iOS and 2.5M on desktop. The 3DTilesRendererJS splat plugin now renders with gaussian-splat-lite, not Spark, and accepts only spz_2-compressed tiles. You therefore have to choose:
   - (a) Strict 'same files everywhere': three.js + 3d-tiles-renderer 0.5.x + the Apache-2.0 3DGS plugin reading the same spz_2 tileset as Luciad and Cesium. The plugin is young and has one maintainer; its WebGPU path falls back to WebGL2.
   - (b) Best three.js quality and tooling: Spark with .RAD (or a flat .spz for the 10x10 m test) generated from the same canonical PLY in the same ENU frame.
   - My recommendation: keep one canonical SH3 PLY in metric ENU as the source of truth. Derive spz_2 3D Tiles for Luciad and Cesium (and the plugin), and a Spark .RAD/.spz for the main public viewer. 'Same data' then means the same frame and source, not literally the same bytes.

3. **Uncompressed debug variant.** Drop 'uncompressed GLB debug variant works everywhere'. It works only in Luciad and Cesium.

4. **Transform matrices.** Add a transform-convention check. Luciad's Affine3DTransformation is row-major; the 3D Tiles 'transform' is column-major. Combine this with the planned L-shaped marker test.

5. **Standards status.** KHR_gaussian_splatting is now ratified ('Complete, Ratified'; it was a release candidate in Feb 2026). spz_2 is still a draft, with active debate as of 2026-09-29 and competing compression proposals (EGSC, L-GSC, MPEG). Keep the splat encoder as a replaceable final stage so tiles can be re-encoded if spz_2 changes or is superseded.

6. **Validation.** Neither 3d-tiles-validator 0.6.1 nor glTF-Validator knows the splat extensions. Rely on the cross-viewer render test, plus a small custom checker: single node, LUF, SPZ magic/version, geometricError monotonic.

7. **Luciad memory budget.** Include maxMemoryUsage (defaults 500 MB CPU / 1000 MB GPU) in the phone/laptop profiles alongside maxSplatCount and maxPointCount.

8. **Tiling tools.** Do not depend on 3DGS-PLY-3DTiles-Converter: its repo returns 404 and its licence is unknown. For LiDAR, py3dtiles 12.1.1 (Apache-2.0, 2026-03-20) is a candidate open LAS/LAZ→PNTS tiler, but its install docs cover Linux only, so test it on Windows early. LuciadFusion 2026.1 remains a fallback if a licence exists.

9. **Licensing.** Keep the licensing questions and make them sharper. The Luciad bundle contains 'Hexagon AB proprietary' myvr components but is now sold by Octave, and splats are not on the Essential/Pro tier page. Ask Octave in writing which tier includes splats and whether a public, anonymous-viewer deployment is allowed.

10. **Hexagon products.** The claim that no Hexagon product combines BLK2GO data with splats in a browser is still unverified; no evidence of one was found. Treat GeoCloud/Reality Cloud Studio as a point-cloud sharing option only.
