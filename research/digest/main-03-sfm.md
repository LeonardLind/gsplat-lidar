# sfm

## Summary

STATE OF THE ART (Oct 2026). COLMAP absorbed most of the open SfM stack in 2026, which makes the front end simpler. The latest release is COLMAP 4.2.1 (2026-09-29), BSD-3-Clause. The official Windows assets are colmap-x64-windows-cuda.zip (395 MB, built with CUDA 13.2, arch all-major, so Ampere sm_86 is fine) and a no-CUDA build. Main milestones:
- 3.11 (2024-11): pose-prior incremental mapper and pose_priors DB table.
- 3.12 (2025-06-30): sensor rigs and frames, plus vocab-tree auto-download.
- 3.13 (2025-11-07): rig consistency checks.
- 4.0 (2026-03-14): GLOMAP merged as `global_mapper` / `automatic_reconstructor --mapper GLOBAL`. ALIKED (N16Rot/N32) extraction and LightGlue matching for SIFT and ALIKED, via ONNX. Pose priors redesigned with position, covariance and gravity. Static Windows CUDA builds.
- 4.1 (2026-06-26): native EQUIRECTANGULAR/spherical camera model (the release notes call it 'faster but less accurate than rendering perspective views'). Also the Caspar GPU BA backend (CASPAR_ENABLED defaults OFF, so probably not in the Windows binary), EUCM, gravity priors, and a pose-prior fix for rigs.
- 4.2 (2026-08-31): LoMa learned features/matchers, multi-component global mapper, browser viewer, pycolmap hierarchical mapping.
The standalone GLOMAP repo (last release 1.2.0, 2025-10-31, which added rigs) was archived on 2026-03-09. pycolmap 4.2.1 has Windows wheels, but they are CPU-only; pycolmap-cuda12 is Linux-only. On Windows, call the CUDA colmap.exe CLI via subprocess and use CPU pycolmap for database/model I/O, rig config, priors and Sim3 alignment. A third-party Windows CUDA pycolmap wheel exists (lyehe/build_gpu_colmap v4.2.0-3, 2026-09-02, CUDA 12.8).

360 → SfM. COLMAP ships its own 360 pipeline: python/examples/panorama_sfm.py on top of pycolmap.panorama, installed with pip 'pycolmap[panorama]'. It can replace the Blender + FFmpeg step for SfM. Its default PERSPECTIVE_OVERLAPPING layout renders 12 SIMPLE_PINHOLE virtual views per equirect frame: 4 yaws × pitches (-35, 0, +35), 90°×90° FOV, width = pano_w×90/360 (8K equirect gives 1920² views), focal = w/(2·tan(hfov/2)). It writes a rig config with zero translation and known rotations, and per-view masks so each panorama pixel yields features only once. It sets rig_verification=True and skip_image_pairs_in_same_frame=True. In BA it fixes rig extrinsics and all intrinsics (ba_refine_sensor_from_rig/focal/pp/extra = False). It supports sequential, exhaustive, vocab-tree and spatial matching and incremental or global mapping, and can convert the result back to an EQUIRECTANGULAR model. Sequential matching orders images by NAME. With expand_rig_images=true (default), each sequential neighbour pair expands to all images of the neighbouring frame. Defaults: overlap 10, quadratic_overlap true, loop_detection false (enable it; period 10, 50 images). Spatial matching reads pose_priors (CARTESIAN or WGS84); defaults ignore_z=true, max_neighbors 50, max_distance 100.

Features and licensing. SIFT is still COLMAP's default and its most tested choice. For forests (low texture, illumination change, limited overlap), the in-COLMAP learned options are ALIKED_N16ROT + ALIKED_LIGHTGLUE (BSD-3 weights + Apache-2.0 matcher) and LoMa (MIT + Apache-2.0, ECCV 2026 oral; it beats ALIKED+LightGlue by about +18.6 mAA on HardMatch and +29.5 on WxBS). Do not mix feature types in one database. Avoid SuperPoint/SuperGlue: the Magic Leap weights are licensed for non-commercial research only, which rules them out for Hexagon work. hloc (Apache-2.0; last tagged v1.4 from 2023, last commit 2025-12-10 for pycolmap 3.13) is now mostly redundant with COLMAP 4.x. It remains useful for MegaLoc (MIT) retrieval to propose pairs between runs. Note that the Windows ONNX runtime COLMAP fetches is the onnxruntime-win-x64-gpu_cuda12 build, while COLMAP itself is built with CUDA 13.2. Check early that ALIKED/LightGlue/LoMa actually run on the GPU.

Feed-forward models do not replace COLMAP here. On 16 GB they handle about 50 to 150 frames per pass, not thousands:
- VGGT: 11.4 GB at 50 frames and 21.2 GB at 100 frames on an H100 (the May 2026 fix gives 2–3× more frames).
- VGGT-Ω: 6.0 GB at 1 frame to 43.2 GB at 500 frames, 624×416, A100.
- MapAnything: up to 2000 views on 140 GB.
Most weights are non-commercial: VGGT-1B, MASt3R (CC BY-NC-SA), VGGSfM (CC BY-NC), Pi3/Pi3X (CC BY-NC), InstantSfM (CC BY-NC-SA according to search; it also lacks Windows support), the DA3 Giant/Large models, and GLUEMAP, which uses Pi3 weights. Commercially usable: MapAnything-apache, VGGT-1B-Commercial (gated, no military use), DA3-Base/Small/Metric-Large (Apache-2.0). GLUEMAP (Pan/Schönberger/Pollefeys, 2026-05) shows feed-forward local inference plus global SfM beating GLOMAP+SIFT on ETH3D (53.0 vs 45.6 AUC@1°). It is Linux-oriented and its weights are non-commercial.

Closed fallbacks:
- RealityScan 2.2 (2026-06-24): imports LAS/LAZ/E57/PTX laser scans and, since 2.1, SLAM trajectories, images and point clouds from handheld scanners. It exports COLMAP (2.1 keeps native distortion), and 2.2 adds an experimental equirect→cube-face workflow. It is free only for legal entities under US$1M revenue, so Hexagon needs a paid seat at US$1,250 per seat per year.
- Agisoft Metashape 2.3.2: Pro costs US$3,499 and supports spherical cameras, multi-camera rigs and marker-based laser-scan alignment. Its COLMAP export for spherical cameras needs converters such as Kotohibi/Metashape_360_to_COLMAP_plane (MIT).

Known poses vs pure SfM. COLMAP accepts LiDAR-derived priors in three ways:
- Soft position priors through pose_prior_mapper / use_prior_position. Default prior_position_loss_scale is 7.815 (chi² 3-DoF 95%); the fallback stddev is 1 m; optional robust loss. Translations cannot be locked (issue #4332, 2026-04).
- Fixed poses through point_triangulator on a hand-made model (cameras/images/points3D, plus rigs.txt/frames.txt in 4.x).
- fix_existing_frames, or constant_rigs, in the mapper.
Fixed poses tie the splat's sharpness to the clap-sync and hand-eye error. With 90° views of 1920 px (f = 960 px), 1° of orientation error is about 17 px. A 33 ms sync error at 30–90°/s handheld rotation gives 1–3°. So the recommended approach is: pure SfM (optionally with soft priors only for pair selection and drift control), then a Sim3 alignment to the LiDAR trajectory. The alignment residuals and the estimated extrinsic then serve as the independent check against the taped/measured offset. Use the fixed-pose path only as a fallback when SfM fragments, for example in tropical forest.

## Recommendations

- **Primary SfM path: COLMAP 4.2.1 Windows CUDA CLI, orchestrated from Python. The CLI handles GPU feature extraction and matching; the CPU pycolmap wheel handles database writes, rig config, priors, model I/O and Sim3 alignment.** — COLMAP is BSD-licensed, actively released (four releases in 2026), and has native rigs, global mapper, ALIKED/LightGlue/LoMa, pose priors and a built-in 360 pipeline, so no non-commercial components are needed. Official pycolmap Windows wheels lack CUDA, so the CLI is the reliable GPU route. _Alternatives:_ lyehe/build_gpu_colmap Windows CUDA pycolmap wheels (third-party), or WSL2 with pycolmap-cuda12 on Linux.
- **Generate SfM images with the pycolmap.panorama approach rather than Blender: 12 virtual SIMPLE_PINHOLE views per equirect frame (4 yaw × pitch -35/0/+35, 90° FOV), ownership masks per view, a rig_config.json with zero translation, and intrinsics and rig fixed in BA (ba_refine_sensor_from_rig/focal/principal_point/extra_params = 0). Merge in extra masks for sky, operator and BLK2GO. Export equirect frames with stabilization and direction lock OFF.** — It is already tested inside COLMAP, it sets rig_verification and skip_image_pairs_in_same_frame, it avoids duplicate features in overlaps, and its exact pinhole intrinsics remove one source of error. Keeping stabilization off keeps the camera-to-BLK2GO extrinsic constant. _Alternatives:_ FFmpeg v360 or Blender crops with a hand-written rig_config.json. A dual-fisheye 2-sensor rig with EUCM/FISHEYE crops, to avoid stitch parallax. Native EQUIRECTANGULAR model for a fast first pass.
- **Matching recipe:
- Name images run1/... and run2/... and use sequential_matcher with expand_rig_images=1, loop_detection=1, overlap of about 5–10, and quadratic_overlap=0 if the pair count explodes.
- For pairs across runs, add vocab_tree_matcher, or MegaLoc retrieval → matches_importer.
- Optionally add spatial_matcher on run-1 LiDAR position priors (ignore_z=0, max_distance about 3–5 m).
- Start with SIFT. Switch to ALIKED_N16ROT+ALIKED_LIGHTGLUE, or LoMa, if registration is under about 95% or the model splits. Never mix feature types in one database.** — Video gives strong temporal adjacency. Loop detection closes the 10 × 10 m loop. Spatial priors stop false loops between look-alike trunks. Learned matchers help most across runs and lighting changes. _Alternatives:_ exhaustive_matcher is feasible only for small subsets of a few hundred images.
- **Mapping: run global_mapper first, which is fast and gives a whole-loop solution. If it fails or splits, fall back to the incremental mapper, or to pose_prior_mapper with soft LiDAR position priors (use_robust_loss_on_prior_position=1, realistic std of about 0.05–0.2 m). Keep at least one pure-SfM solution without priors for the independent extrinsic check.** — The global mapper is 1–2 orders of magnitude faster with comparable quality. Incremental is more forgiving of outlier loops. Using priors in the reconstruction contaminates an 'independent' estimate of the offset. _Alternatives:_ hierarchical_mapper for very long tropical runs.
- **Registration to LiDAR: Sim3-align the SfM camera centres of run-1 frames to the LiDAR trajectory interpolated at the clap-synced timestamps (model_aligner or pycolmap.align_reconstruction_to_locations, with RANSAC), estimating the time offset as well. Then refine with ICP between SfM or MVS points and the LiDAR cloud, and report the extrinsic and residuals against the tape-measured prior.** — This avoids baking sync and hand-eye errors into the poses: about 17 px of error per 1° of orientation error. Run 2 has no LiDAR, so it is co-registered through the joint SfM. _Alternatives:_ Hand-eye solve (AX = XB) on relative motions, if the trajectory includes orientations.
- **Fallback A (known poses): build a COLMAP model from LiDAR trajectory × measured extrinsic × virtual-view rotations (cameras/images/rigs/frames txt), run point_triangulator, then a pose_prior_mapper or BA pass with poses free but softly constrained. Fallback B: RealityScan with a paid seat (LAS/E57 + SLAM import, COLMAP export) or Metashape Pro. Fallback C: MapAnything-apache or VGGT-1B-Commercial on chunks of 50–150 frames as initialization only, followed by COLMAP BA.** — These cover failure in dense tropical forest without making closed or non-commercial tools a dependency. _Alternatives:_ GLUEMAP/Pi3 is research-only (non-commercial weights).
- **Don't use SuperPoint/SuperGlue, MASt3R, VGGSfM, Pi3/GLUEMAP, the original VGGT-1B, DA3-Giant/Large or InstantSfM in a Hexagon deliverable.** — Their licenses are non-commercial (CC BY-NC / NC-SA, or Magic Leap research-only). InstantSfM is also unsupported on Windows. _Alternatives:_ ALIKED, DISK or LoMa with LightGlue; MapAnything-apache; DA3-Base/Small; VGGT-1B-Commercial.

## risks

- The Windows COLMAP CUDA 13.2 binary bundles the ONNX Runtime gpu_cuda12 build. ALIKED/LightGlue/LoMa may silently run on the CPU, which would make learned matching on thousands of images take hours. Check this on the first test.
- Not all Windows laptop drivers support CUDA 13.2. The official CUDA binary may need a driver update to R580+ (my understanding, not verified).
- With rig expansion, sequential matching produces about 2000 candidate pairs per 12-view frame. Matching time grows quickly, especially with LightGlue (about 50–150 pairs/s on an RTX 3080).
- Global SfM is sensitive to false loop closures between look-alike trees. Validate with LiDAR priors (pose_prior residuals) and compare against an incremental run.
- If FlowState, horizon lock or direction lock is on in the Insta360 export, the camera-to-LiDAR extrinsic varies per frame and the software-vs-measured offset check becomes meaningless.
- The operator and BLK2GO appear in every 360 frame (the camera is taped under the BLK2GO). Without masks they create camera-fixed false matches and also artefacts in the splat.
- Equirect stitching parallax on nearby branches (under about 1–2 m) corrupts matches near the stitch seam. Masking seams or using the raw dual-fisheye images mitigates this.
- Rolling shutter and motion blur from walking under the canopy are not modelled by COLMAP.
- The clap-based time sync gives at best about ±1 frame (33 ms). That is too coarse to use LiDAR poses as fixed camera poses for 3DGS.
- RealityScan's free tier does not apply to Hexagon (revenue threshold on the whole legal entity). VGGT-Commercial and SAM 3 exclude military/ITAR uses, so check Hexagon's business units if relevant.
- hloc lags pycolmap 4.x (its last compatibility work targets pycolmap 3.13), so integration may break.
- WebSearch budget was exhausted mid-research. Forest-specific failure modes and some RealityScan, Metashape and Insta360 details rest on background knowledge or secondary sources.

## FACT-CHECK: recommendation assessment

The core recommendation holds: COLMAP 4.2.1 (BSD-3) as the primary SfM, SIFT first, ALIKED+LightGlue or LoMa second, a rig of virtual pinhole views, pure SfM followed by Sim3 alignment to LiDAR, and fixed LiDAR poses only as a fallback. Versions, dates, defaults, licences and the global-mapper merge all checked out against primary sources. The things I would change:

(1) Do not run panorama_sfm.py end to end on Windows. pycolmap is CPU-only there, and pycolmap.panorama hard-codes SIFT through default FeatureExtractionOptions and keeps the rig config only in memory. Use render_perspective_images() (or FFmpeg v360 or OpenCV remap with the same 12-view layout) to write images and masks. Write rig_config.json yourself and run feature_extractor, rig_configurator, the matchers and the mappers through colmap.exe. Alternatives: the lyehe CUDA pycolmap wheel, or WSL2 with pycolmap-cuda12.

(2) Treat the ONNX GPU issue as a setup step, not a low-probability risk. The official zip ships only CUDA 13 cudart and curand, while the ONNX execution provider is the CUDA 12 build. Install a CUDA 12 runtime and cuDNN 9, or use the lyehe CUDA 12.8 build, which also brings Caspar GPU bundle adjustment on Windows. Check the driver is 580 or newer.

(3) For global_mapper, explicitly disable refine_sensor_from_rig and intrinsics refinement; it defaults to true outside panorama.py. Note that the global mapper ignores position priors, so LiDAR priors only help through spatial_matcher pair selection. Drift control with priors means pose_prior_mapper, which is incremental.

(4) Matching: set quadratic_overlap=0. Its 2^i offsets reach +512 frames, which, multiplied by the 12×12 rig expansion, gives about 2300 pairs per frame. Use loop detection and spatial pairs (ignore_z=0, a few metres) instead. Cut the frame rate (about 1–2 fps, or every 0.25–0.5 m) for a 10×10 m loop. Expect LightGlue through ONNX to be slower than the README's PyTorch figure of 50–150 FPS.

(5) Registration: do not Sim3-align SfM camera centres directly to LiDAR body positions. The BLK2GO-to-Insta360 lever arm (about 0.1–0.3 m) is a large fraction of a 10 m loop and will bias the fit. Jointly estimate Sim3, lever arm, rotation extrinsic and time offset, which needs trajectory orientations, or run an AX=XB hand-eye solve, then ICP. Once the time offset is estimated, the 33 ms clap bound mostly goes away; still keep a prior-free SfM run for the independent extrinsic check.

(6) Licences: add VGGT-Ω (FAIR Noncommercial) to the do-not-use list. InstantSfM is CC BY-NC 4.0, not NC-SA. GLUEMAP is not inherently non-commercial (it supports MapAnything-apache and VGGT-Commercial backbones) but carries GPL-3.0 SALAD retrieval.

(7) Fallbacks: Metashape Pro is a better commercial fallback than stated, because it has native COLMAP export since 2.2. RealityScan still needs a paid seat (US$1,250 per seat per year) for Hexagon. For Fallback C, consider VGGT-Long-style chunking with VGGT-1B-Commercial, which is shown on 4500 frames with 24 GB, and still finish with COLMAP BA.

Unverified: the Insta360 stabilisation-off requirement (vendor pages unreachable; test it), the EUR RealityScan price, OPENCV_FISHEYE behaviour at 90° or more, and the actual ALIKED vocab-tree URL. WebSearch budget was exhausted early, so all checks used direct WebFetch of primary sources.
