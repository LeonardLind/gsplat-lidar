# gap: windows-toolchain

## Summary

Bottom line: the stack most likely to work on the RTX 3080 Ti Laptop (sm_86, 16 GB) under Windows 11 in October 2026 uses ONE CUDA toolkit, 12.8.1, and torch 2.8.0+cu128. The official COLMAP 4.2.1 CUDA zip runs next to it on the driver alone; it needs no CUDA 13 toolkit. Partway through, the shared web-search budget ran out. Everything after that point came from fetching known primary URLs, so a few items have only one source.

(1) Driver. NVIDIA's R595 release notes list GeForce RTX 30 notebook GPUs as supported. Tom's Hardware and VideoCardz report that 595.71 fixed a fan-detection bug in 595.59 that hit RTX 30, 40 and 50 cards, so skip 595.59. Driver branches map to CUDA versions like this: 13.0 to R580, 13.1 to R590, 13.2 to R595, 13.3 to R610, 13.4 to R615 (the latest is 13.4 U1). Any CUDA 13.x app runs on driver 580 or newer through minor-version compatibility. R580 was the last branch for Maxwell, Pascal and Volta; Ampere is unaffected. On laptops NVIDIA only says the OEM provides 'certified' drivers, and gives no hard block. The machine runs Windows 11 Home (build 26200), so corporate driver lockdown is unlikely. Windows Update can still roll the driver back to an older OEM one. Install the latest R595-or-newer Studio or Game Ready driver from nvidia.com, then check that nvidia-smi shows 580 or higher.

(2) COLMAP ONNX on the GPU. The 4.2.1 Windows CI builds with CUDA 13.2.0 on windows-2025-vs2026 using -allow-unsupported-compiler. It targets all-major architectures (75 to 120); the sm_80 machine code runs on sm_86. It copies only cudart64_*.dll and curand64_*.dll into the zip. Meanwhile FindDependencies.cmake downloads onnxruntime-win-x64-gpu_cuda12-1.30.0. ONNX Runtime 1.27 to 1.30 CUDA-12 builds need CUDA 12.8 or newer plus cuDNN 9. So the shipped GPU provider has no matching CUDA 12 runtime, cuBLAS or cuDNN. COLMAP's onnx.cc calls AppendExecutionProvider_CUDA and turns ONNX Runtime exceptions into an error. That suggests a missing DLL makes it fail loudly rather than quietly drop to CPU (medium confidence, from reading the code). Issue #4787 (Sept 30, 2026; RTX 5090, cuDNN 9.27 on PATH) shows the CUDA provider working with BF16 LoMa extraction. Only the BF16 LoMa matcher fails ('CPU EP fallback disabled') and falls back to FP32. That is indirect proof that adding CUDA 12 runtime plus cuDNN 9 to PATH works. I found no Ampere-specific report. Practical fix: launch COLMAP from a .bat that puts CUDA 12.8\bin and the cuDNN 9 CUDA-12 bin folder first on PATH. The alternative is lyehe's CUDA 12.8 bundle.

(3) gsplat on Windows. PyPI's latest is still 1.5.3 (July 2025). Main says version 1.6.0 (bumped Aug 14, 2026, commit c3d59bb); its newest commit is 512d366 (Sept 19, 2026). The prebuilt wheel index stops at pt24/cu124 for Python 3.10. Main does not currently build with MSVC:
- `__builtin_clzll` in RasterizeToPixelsFromWorld3DGSParallelBatchBwd.cu (issue #1007 and PR #1008, open since July 7, 2026).
- PR #1055, open since Sept 5, 2026, lists: C3861, C3495 constexpr lambda capture, LNK2001 const mismatch, and `at::cuda::cub radix_sort_pairs_impl<int64_t,4>` not exported from torch_cuda.dll.
- CUDA 13 only (also in #1055): CCCL 3.0 breakages (std::isfinite, std::array, uint).

PR #1055 is the only documented Windows-working gsplat 1.6 setup: Windows 11, RTX 4060 Laptop, CUDA 13.0, MSVC 19.44, torch 2.9.1+cu130. gsplat's wheel CI matrix covers torch 2.8.0, 2.9.1 and 2.10.0 with cu126 to cu130 on windows-2022, minus cu126 ('CUDA 12.6 incompatible with MSVC >= 14.44'). setup.py requires torch 2.7 or newer.

The torch version matters a lot on Windows:
- torch 2.9 to 2.11 builds extensions as C++17. Any nvcc-compiled file that includes torch/extension.h then fails with 'C2872 std ambiguous' in compiled_autograd.h (pytorch PR #188952 still open; issue #148317; Inria issue #1215 says 'avoid 2.9+').
- torch 2.12 and later build as C++20 and avoid this, but they ship no cu128 wheels (only cu126, cu130, cu132).
- cu128 wheels end at 2.11.0. The latest torch is 2.14.1.
- fused-ssim's ssim.cu includes torch/extension.h, so it is exposed. fused-ssim issue #42 also shows a torch 2.10.0+cu128 header failure (my reading: the Windows `small` macro).
- torch 2.8.0+cu128 is chosen independently by 3DGRUT's CUDA 12.8 default and by the Inria issue #1215 recipe.

(4) PPISP is small. Its CUDA source includes only c10/cuda headers, and it has no reported Windows issues across its 6 issues. Its Windows build is likely fine but untested.

(5) lyehe/build_gpu_colmap v4.2.0-3 (Sept 2, 2026) is built on COLMAP 4.2.0, not 4.2.1. It uses CUDA 12.8 with the runtime bundled on Windows and needs driver 570 or newer. It ships CPU, CUDA-Caspar and CUDA-cuDSS-Caspar zips (the CUDA one is 1.74 GB), plus pycolmap win_amd64 wheels for Python 3.10 to 3.14, under the Unlicense. Official PyPI pycolmap 4.2.1 on Windows is CPU-only; gsplat needs pycolmap only to parse the data.

(6) 3DGRUT install_env_uv.ps1 needs Python 3.11 and finds vcvarsall by glob. It adds --allow-unsupported-compiler for newer Visual Studio versions. It maps CUDA 12.8.1 to torch 2.8.0 (architecture list includes 8.6) and CUDA 13.0.2 to torch 2.13.0 (experimental; architecture list skips 8.6). It builds tiny-cuda-nn from source and uses Kaolin wheels only up to CUDA 12. I found no laptop-specific reports. A libigl build failure (#239) was closed in April 2026.

(7) Multiple CUDA toolkits. Each install changes CUDA_PATH, so NVIDIA says to check it after every install or uninstall. torch stops on a major-version mismatch between nvcc and torch ('detected CUDA version ... mismatches'). CUDA 12.8 supports VS 2019 and VS 2022 17.x only. CUDA 13.2 adds VS 2026 (MSVC 195x).

(8) Inria gaussian-splatting still ships environment.yml with CUDA 11.6, torch 1.12.1 and Python 3.7. The known-good Windows recipe (#1215) is Python 3.10, torch 2.8.0+cu128, CUDA 12.8, VS 2022, DISTUTILS_USE_SDK=1, --no-build-isolation, '#include <float.h>' in simple-knn, and KMP_DUPLICATE_LIB_OK. Taming 3DGS's rasterizer speed-ups are merged into Inria (about 1.6x by default, 2.7x with sparse_adam). Taming has no Windows issues filed.

(9) Spark v2.3.1 (Oct 1, 2026). build-lod is a Rust crate (`npm run build-lod` or `cargo run --release`) whose default 'gpu' feature uses wgpu. It writes *-lod.rad, plus .radc chunks with --rad-chunked. PotreeConverter is at 2.1.5 (Sept 23, 2026; 2.1.4 added brotli and split stages). The README still says to build with VS 2019.

Plan impact: one venv for gsplat/PPISP on CUDA 12.8 and torch 2.8.0, with PR #1055's MSVC fixes applied. Separate venvs for 3DGRUT (Python 3.11, its script, CUDA 12.8) and optionally Inria (torch 2.8.0). The COLMAP 4.2.1 official zip for SIFT and the GUI; for ALIKED/LightGlue on the GPU, add CUDA 12.8 and cuDNN 9 to PATH, or use the lyehe 4.2.0 build. All code, venvs and caches go in paths without spaces (C:\dev). TEMP already uses the 8.3 short name C:\Users\LEONAR~1, which avoids the space.

## Recommendations

- **Driver: install the latest NVIDIA Studio or Game Ready driver for the RTX 3080 Ti Laptop from nvidia.com, R595 or newer (R610/R615 is fine), and avoid 595.59. Afterwards check that nvidia-smi shows driver >= 580 and 'CUDA Version 13.x'. If Windows Update rolls back to an OEM driver below 580, pause driver updates through Windows Update.** — One driver at or above R595 covers the CUDA 13.2 COLMAP build natively, the torch cu128 wheels and any later cu130 move. RTX 30 notebooks are supported, and 595.59 had a fan bug on RTX 30. _Alt:_ The OEM-certified driver works only if it is >= 580; anything older breaks the official COLMAP 4.2.1 CUDA build.
- **Host compiler: Visual Studio 2022 Build Tools 17.14 (MSVC 14.44, v143) as the only C++/CUDA host compiler. If VS 2026 is already installed, add the v14.44 toolset and call `vcvarsall.bat x64 -vcvars_ver=14.44`.** — CUDA 12.8 officially supports only VS 2019 and VS 2022. gsplat CI shows MSVC 14.44 needs CUDA 12.8 or newer, and PR #1055's patches were tested on MSVC 19.44. _Alt:_ VS 2026 with -allow-unsupported-compiler (COLMAP and 3DGRUT do this) is acceptable with CUDA 13.2 or newer, which supports MSVC 195x officially.
- **CUDA toolkits: install only CUDA 12.8.1 system-wide (with cuDNN 9.x for CUDA 12 for COLMAP's ONNX Runtime). Do not install a CUDA 13 toolkit unless the cu130 fallback below is used. In every venv activation script, set CUDA_HOME=CUDA_PATH=<v12.8> and put v12.8\bin first on PATH. Set TORCH_CUDA_ARCH_LIST=8.6, DISTUTILS_USE_SDK=1 and MAX_JOBS=4.** — The official COLMAP zip carries its own cudart64_13 and needs only the driver. One 12.8 toolkit serves the gsplat, PPISP, fused-ssim, 3DGRUT and Inria builds and also supplies the CUDA 12 runtime DLLs that COLMAP's ONNX Runtime needs, which avoids CUDA_PATH and cuDNN mix-ups. _Alt:_ Add CUDA 13.0.2 or 13.2 side by side only for a cu130 experiment, switching per venv and never via the global CUDA_PATH.
- **Main training venv: Python 3.11; torch 2.8.0 + torchvision 0.23.0 from the cu128 index. gsplat = main as of PR #1055's head (or main at 512d366 with the MSVC parts of #1055 applied: the __builtin_clzll/_BitScanReverse64 change, C3495, the LNK2001 const fix and the cub radix-sort replacement), installed with `pip install . --no-build-isolation`. Then ppisp v1.2.1, fused-ssim@a7c48d6 and fused-bilagrid@49f0ef0, all built with --no-build-isolation. Use CPU pycolmap 4.2.1 from PyPI for parsing only. Edit examples/requirements.txt so torch and torchvision stay at 2.8.0 and 0.23.0.** — torch 2.8.0+cu128 is inside gsplat's own CI matrix (setup.py needs torch 2.7 or newer), is what 3DGRUT and the Inria recipe choose independently, and avoids the C2872 error that torch 2.9 to 2.11 trigger in fused-ssim's ssim.cu. CUDA 12.8 also avoids the CCCL 3.0 breakages that are specific to CUDA 13. _Alt:_ Fallback A, the exact #1055 setup: CUDA 13.0.x plus torch 2.9.1+cu130 with the full #1055 branch, and a local patch to site-packages/torch/include/torch/csrc/dynamo/compiled_autograd.h copied from pytorch PR #188952 (needed for fused-ssim). Fallback B: torch 2.12 to 2.14 with cu130 or cu132 and the CUDA 13.x toolkit (C++20 avoids C2872; untested with gsplat).
- **COLMAP: use the official 4.2.1 colmap-x64-windows-cuda.zip for SIFT, matching, GLOMAP and the GUI. For ALIKED, LightGlue or LoMa on the GPU, launch it from a colmap_gpu.bat that puts CUDA v12.8\bin and the cuDNN 9 CUDA-12 bin folder first on PATH. Check that extraction does not print 'ONNX Runtime error' and that GPU load shows in Task Manager or nvidia-smi. Keep LoMa in FP32 (the BF16 matcher fails, #4787).** — The zip ships the cuda12 ONNX Runtime provider without its CUDA 12, cuBLAS or cuDNN dependencies. 4.2.1 fixes the LoMa GPU memory leak and the illegal memory access on large images, which matters for high-resolution 360 frames. _Alt:_ lyehe COLMAP-4.2.0-windows-2022-CUDA-Caspar.zip (CUDA 12.8 bundled, 4.2.0 without the 4.2.1 fixes), or a lyehe pycolmap cp311 win_amd64 CUDA wheel in a separate venv if GPU SfM from Python is needed.
- **3DGRUT in its own venv: run install_env_uv.ps1 with CUDA 12.8 (its default: torch 2.8.0, Python 3.11). Clone it to a path without spaces. Treat 3DGRT/3DGUT as optional until gsplat's built-in 3DGUT is tested.** — The script's CUDA 12.8 setup matches the main matrix; its CUDA 13.0 setup is experimental and its architecture list skips 8.6. _Alt:_ Use gsplat's built-in 3DGUT (fisheye and distorted cameras) and skip 3DGRUT.
- **Optional Inria (with Taming's accelerated rasterizer) venv: Python 3.10 or 3.11, torch 2.8.0+cu128, CUDA 12.8, VS 2022, add '#include <float.h>' to simple-knn and use --no-build-isolation. Use it as a quality and depth-regularization baseline only.** — The non-commercial licence is fine for this project, and depth regularization and exposure compensation are useful references. On Windows, though, gsplat stays the better main trainer (Apache, PPISP, MCMC cap_max for the 16 GB budget, 3DGUT, active maintenance). _Alt:_ The Taming 3DGS repo directly, for budget modes (final_count); same build constraints.
- **Paths: put all repos, venvs, caches and torch extension builds under C:\dev (set TORCH_EXTENSIONS_DIR, UV_CACHE_DIR, PIP_CACHE_DIR, TORCH_HOME and HF_HOME there). Never build inside C:\Users\Leonard Lind\... TEMP already resolves to the 8.3 path C:\Users\LEONAR~1\AppData\Local\Temp (seen in this session), which is safe.** — The default JIT and extension directories, and several build tools, live under the profile path, which contains a space. I found no fresh 2026 evidence of space bugs, but avoiding them costs almost nothing. _Alt:_ Rely on the 8.3 short names, which is fragile if 8.3 name creation is ever turned off.
- **Web delivery tools: Rust stable MSVC toolchain (rustup) for Spark build-lod, run with `cargo run --release` from a path without spaces; if wgpu picks the integrated GPU, use --no-default-features. Use the PotreeConverter 2.1.5 Windows binary rather than building from source.** — Both have current releases (Spark v2.3.1, Oct 1, 2026; PotreeConverter 2.1.5, Sept 23, 2026). build-lod's default gpu feature uses wgpu. _Alt:_ Spark's browser-side LoD build for small scenes; LuciadRIA or HSPC tooling for the LiDAR layer instead of Potree.
