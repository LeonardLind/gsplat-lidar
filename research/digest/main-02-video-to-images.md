# video-to-images

## Summary

Bottom line: for this project, turn 360 video into training images with a Python reframer (cv2.remap or equilib/torch) that copies COLMAP's own panorama-rig method, then run SfM with the COLMAP >=4.2 Windows CLI as a fixed virtual rig. Blender is not needed. It does the same gnomonic math as cv2.remap, only much slower, and it adds pitfalls (Cycles pixel-filter blur, AgX/Filmic tone mapping, axis-convention conversion). FFmpeg stays as the decoder and frame/timestamp extractor. v360 is a fine fallback reframer, but its yaw-sign and pixel-centre conventions must be checked against the rig extrinsics you write.

State of the art (Oct 2026). COLMAP 3.12.0 (2025-06-30) added sensor rigs and the panorama_sfm.py example. The example exists and calls pycolmap.panorama.reconstruct. It renders each equirect into virtual pinhole views and registers them as a rig with known extrinsics. It fixes intrinsics and the rig (ba_refine_sensor_from_rig=False, focal/principal-point/extra params fixed) and runs the sequential matcher with the incremental or global mapper. Layouts: PERSPECTIVE_OVERLAPPING (the default) is 12 views (4 yaws x pitch -35/0/+35, 90x90 deg, SIMPLE_PINHOLE, f=w/2, w=pano_w*90/360, so 1920 px from 8K). PERSPECTIVE_NON_OVERLAPPING is 4 horizon views. SPHERICAL uses the native EQUIRECTANGULAR model added in COLMAP 4.1.0 (2026-06-26). Since 4.1 the example can also convert a perspective-rig solve back to equirect. It writes internal 'uniqueness' masks so each panorama pixel yields features in only one virtual view. It does NOT accept user masks for the operator or rig, so we must fork it or reimplement it (BSD-3, about 700 lines). COLMAP 4.0.0 (2026-03-14) built GLOMAP in as global_mapper and added ALIKED/LightGlue. 4.2.0 (2026-08-31) improved sequential pairing for rigs. The latest is 4.2.1 (2026-09-29). On Windows, pip pycolmap is CPU-only (pycolmap-cuda12 is Linux-only), so GPU SIFT should go through the colmap.exe binaries.

Other options:
- nerfstudio ns-process-data (equirect): 8 views at 120 deg or 14 at 110 deg, no rig. nerfstudio's last release was v1.1.5 (Nov 2024) and it has open artifact/crop bugs.
- AliceVision Split360Images: a yaw-only ring (default 2 splits, 110 deg, 1200 px) with a rig in its SfMData, so no up/down views.
- py360convert (MIT) and equilib (Apache-2.0, torch GPU): good remap libraries, but you write the rig JSON yourself.
- Native-sphere SfM: SphereSfM (BSD-3), OpenMVG (used by ODGS/OmniGS), Metashape spherical (commercial), and now COLMAP SPHERICAL.
- Equirect-native or fisheye splat training: LichtFeld Studio v0.5.3 (2026-07-01, GPLv3) supports equirect and 3DGUT. gsplat 1.5.3 supports 3DGUT fisheye (MCMC only). 3DGRUT v2.0.0 is Apache-2.0. Research 360-GS methods (ODGS MIT, OmniGS GPL-3, 360-GS, PFGS360 CVPR'26, Seam360GS ICCV'25) are research code.
- Dedicated 2025-26 tools: lichtfeld-360-plugin (GPL-3, Windows-first, SAM 3 masking, COLMAP 4.1 rigs, presets of 6/12/16/20/24 views at 90 deg, native fisheye/ERP modes, v0.5.0 Aug 2026) is the closest turnkey match and a good benchmark. 360toolkit (MIT source, uses the Insta360 MediaSDK and SAM3.cpp). Moshpit360 is not released yet. insta360-rs (Apache-2.0, experimental 0.1) reads factory calibration and exports deterministic-seam equirect or per-lens fisheye with stabilisation off. insv-stitch (MIT, X5, Linux) measured the X5 rolling-shutter readout at about 21 ms.

Ranking for this project (quality, rig consistency, speed, Windows/Python):
1. Custom remap plus COLMAP CLI rig, i.e. pycolmap.panorama logic with user masks.
2. pycolmap.panorama as-is, as a baseline with no operator masks.
3. lichtfeld-360-plugin, as a GUI benchmark.
4. FFmpeg v360 with a hand-written rig JSON.
5. Dual-fisheye native: a 2-lens OPENCV_FISHEYE rig and a 3DGUT trainer. Highest ceiling, no stitch seams, and the best route later for dense tropical forest with close range parallax, but more complex. A VISAPP'26 study found 160 deg crops beat 200 deg.
6. COLMAP SPHERICAL plus LichtFeld equirect training.
7. Blender.
8. nerfstudio.
9. AliceVision.

Layout: use 16 views at 90x90 deg: 8 at horizon (yaw every 45 deg, about 50% overlap), 4 at pitch -40 to -45, 4 at +40. Drop explicit zenith and nadir views. Run 1's zenith is the BLK2GO and hand; Run 2's nadir is the operator. Denser horizon views let each feature be extracted within about ±22 deg of a view's centre, which means less perspective stretching. For speed or storage, COLMAP's 12-view layout is the fallback. Resolution: 1920 px from 8K (1:1 centre sampling would be about 2440 px) or 1440 px from 5.7K. Downscale to about 1600 px for training.

Frames: aim for 0.2-0.3 m spacing (forest objects at 1-2 m need parallax without big appearance change). At 0.5-0.7 m/s that is about 2-3 panos/s. Take candidates at 6 fps from the 30 fps video and keep the sharpest per 0.3-0.5 s window (Laplacian variance or Tenengrad on masked, downscaled frames). In Run 1, select by distance along the BLK2GO trajectory once time-synced. Use mpdecimate or a motion test to drop stationary segments. Expect about 130-200 panos per 40 m loop, 300-400 for both runs, so 3-6k perspective images.

Masking: one static rig mask (BLK2GO plus hand) painted once in equirect and remapped into every view. This only works with FlowState, Direction Lock and Horizon Lock OFF at export. Plus per-frame operator masks from SAM 3/3.1 (SAM License), SAM 2.1 (Apache-2.0) or Grounded-SAM-2. Run them on each virtual-view stream as a video (equirect detection near the poles and seams is poor), dilate +10-20%, and include shadows. For COLMAP, AND the operator/rig mask with the uniqueness mask and pass it as ImageReader.mask_path (black = no features; file named <image>.jpg.png). For training, pass only the operator/rig mask, in ignore-in-loss mode: Brush masks/ (black ignored), nerfstudio mask_path, LichtFeld Ignore mode, 3DGRUT *_mask.png. gsplat simple_trainer needs a small patch. Never use alpha/transparency or 'segment' modes for occluders. Never paint the operator black in the pixels.

Main pitfalls:
- Stabilisation and horizon lock rotate the sphere every frame. That breaks static masks and the fixed camera-to-BLK2GO extrinsic.
- Stitch seams with close-range parallax and optical-flow restitching.
- Colour differences between the two lenses: use chromatic calibration plus appearance modelling in the trainer.
- Rolling shutter (about 21 ms on the X5).
- Motion blur under canopy: use a shutter of 1/250 s or faster.
- Losing frame timestamps (needed for LiDAR sync). Use select with -frame_pts or PyAV pts, not the fps filter.
- 3-6k images at 1600-1920 px exceed RAM caching, so use trainers that stream from disk.

## Recommendations

- **Replace the Blender virtual-camera step with a Python reframer: cv2.remap with lookup maps precomputed once per view, or equilib on the GPU, following pycolmap.panorama's math (SIMPLE_PINHOLE, f=w/2 for 90 deg). Write rig_config.json with exact rotations and zero translation, and run COLMAP 4.2.x via the Windows colmap.exe CLI.** — Same geometry as Blender with none of the colour, filter-blur or axis-convention pitfalls and far faster. It also gives full control over layout, user masks (pycolmap.panorama has no user-mask input) and timestamps, and uses GPU SIFT on Windows, where pip pycolmap is CPU-only. The rig constraint (ba_refine_sensor_from_rig=0, fixed intrinsics) is what makes 360 SfM robust. _Alternatives:_ Quickest baseline: run panorama_sfm.py unchanged on CPU, without operator masks. GUI benchmark: lichtfeld-360-plugin. Fallback reframer: FFmpeg v360 with split into N outputs, after checking its yaw sign and pixel-centre convention.
- **Capture: X5 at 8K30 (or X6 8K at 30-50) in 360 video mode, H.265 high bitrate, manual shutter of 1/250-1/500 s, ISO auto with a cap, fixed white balance, exposure locked. Walk 0.5-0.7 m/s with slow turns. Do each loop twice in opposite directions so the region behind the operator is seen unoccluded. Rigid mount with lens axes left/right of travel, operator directly behind. Run 2: invisible selfie stick extended well above head height.** — Motion blur at 1 m/s and 1 m range: 1/60 s gives about 1 deg, about 21 px at 8K; 1/250 s gives about 5 px; 1/500 s gives about 2.5 px. Locked exposure and white balance avoid flicker. Walking both directions gives masked regions coverage. Niantic and freegaussian guides back the lens orientation, slow pace and overhead stick. _Alternatives:_ 5.7K60 if low light under tropical canopy forces it. This is a resolution trade-off; whether low-light behaviour is better was not verified.
- **Export without stabilisation: Insta360 Studio or MediaSDK with FlowState OFF, Direction Lock OFF, Horizon Lock OFF, chromatic calibration ON, colour enhancement OFF, full-resolution equirect H.265 high bitrate (or an image sequence). Keep audio and do not trim, to preserve the clap timeline. Later, evaluate insta360-rs for deterministic-seam equirect or per-lens fisheye export.** — Keeps the equirect frame rigidly attached to the camera body, as needed for static BLK2GO masks and a constant camera-to-LiDAR extrinsic. Horizon Lock is on by default in Insta360 tools. _Alternatives:_ Native dual-fisheye route: extract the two .insv tracks, crop each lens to about 160-180 deg with a circular mask, build a 2-sensor OPENCV_FISHEYE rig (rig_configurator estimates the lens-to-lens extrinsic), and train with 3DGUT (gsplat, LichtFeld or 3DGRUT). This avoids seams, which matters for close-range forest parallax, but needs fisheye-capable trainers.
- **Virtual camera layout: 16 views at 90x90 deg. 8 at pitch 0 (yaw 0..315, step 45); 4 at pitch -40 to -45 (yaw 45+90k); 4 at pitch +40 (yaw 45+90k). No explicit zenith or nadir views. 1920 px from 8K (1440 px from 5.7K) for SfM, about 1600 px for training. Use Voronoi uniqueness masks (each panorama pixel goes to the nearest view axis) for feature extraction only.** — Denser horizon views keep each feature within about ±22 deg of a view centre, with less stretch than the 45 deg edges of a 4-view ring, so cross-frame matching improves. Adjacent horizon views overlap about 50%. The ±40 rings reach about ±85 deg, covering ground (needed for LiDAR ground and registration) and canopy while dropping the BLK2GO zenith and operator nadir. The uniqueness masks avoid duplicate tracks from views that share an optical centre. _Alternatives:_ COLMAP's default of 12 views (4 yaws x pitch -35/0/+35, 90 deg), validated upstream and lighter on storage. Or 18-24 view spirals, which give diminishing returns.
- **Frame selection: decode with NVDEC and keep exact timestamps (ffmpeg select='not(mod(n\,5))' -fps_mode passthrough -frame_pts 1, or PyAV pts), giving 6 fps candidates from 30 fps. Score sharpness by Laplacian variance or Tenengrad on 1/4-scale frames inside unmasked, non-seam regions. Keep the sharpest per 0.3-0.5 s window, targeting about 0.2-0.3 m spacing. In Run 1, after time sync, resample by distance along the BLK2GO trajectory (every 0.25 m or 10 deg of rotation). Drop stationary segments with mpdecimate or a flow-magnitude test.** — A 40 m loop at 0.5-0.7 m/s gives about 130-200 panos per loop, about 300-400 for both runs, so 4.8-6.4k images at 16 views (3.6-4.8k at 12). This gives roughly 10-15 deg parallax on trunks 1 m away. The fps filter retimes frames and would break LiDAR sync. _Alternatives:_ sharp-frames-python (batched mode). For Run 2 without LiDAR: a quick low-resolution SfM first, then resample by the estimated trajectory distance.
- **Masking pipeline: (1) a static rig mask for BLK2GO plus hand, painted or SAM-segmented once on an equirect, remapped (nearest neighbour) into each view and dilated about 15 px. (2) Per-frame operator masks from SAM 3/3.1 text prompt 'person' (or SAM 2.1 / Grounded-SAM-2 if the SAM License is a concern), run per virtual-view sequence as video, dilated +10-20%, shadows included. (3) The COLMAP mask is (NOT operator AND NOT rig AND uniqueness), written to mask_path/<subpath>/<name>.jpg.png. (4) The training mask is (NOT operator AND NOT rig), in the trainer's ignore format: Brush masks/, nerfstudio mask_path, LichtFeld Ignore mode, 3DGRUT *_mask.png, or a small loss-mask patch for gsplat.** — Features fixed to the camera must never reach SfM. Ignore-in-loss leaves occluded pixels unsupervised instead of carving transparent holes, which alpha or segment modes would. Equirect-space detection is unreliable near the poles and seams. _Alternatives:_ YOLO26-seg (AGPL-3.0) as a fast detector feeding SAM box prompts. Or the lichtfeld-360-plugin's built-in SAM 3 masking.
- **SfM settings: register Run 1 and Run 2 as separate rigs with identical geometry, using image prefixes run1/camXX and run2/camXX. Run sequential matching within each run (overlap about 10-20 frames, loop detection on to close the 10x10 m loop) plus vocab-tree or retrieval matching across runs. Use the mapper with ba_refine_sensor_from_rig 0 and all ba_refine_* intrinsics 0, or global_mapper for speed. Export as PINHOLE images plus the sparse model.** — Uses exact virtual-rig constraints and COLMAP 4.2's rig-aware sequential pairing. Combining both runs gives the splat its second viewpoint height. Note: the lichtfeld-360-plugin claims the global mapper lacks rig support, while 4.1 fixed rotation averaging with multi-image rigs, so test both. _Alternatives:_ COLMAP SPHERICAL (equirect-native) reconstruction, or panorama_sfm's convert_to_equirectangular, for trainers that accept equirect (LichtFeld v0.5.3).

## risks

- Stitch-seam parallax and optical-flow restitching in close-range forest (trunks within 1-2 m) cause geometry that differs from frame to frame along the seams, which shows up as floaters. Mitigate with lens orientation, masking the seam neighbourhood, deterministic stitching (insta360-rs) or the dual-fisheye route.
- Colour/exposure differences between the two lenses make views that straddle the seam inconsistent. Mitigate with chromatic calibration plus per-image appearance compensation in the trainer (e.g. gsplat app_opt or bilateral grid, 3DGRUT PPISP); locked exposure and white balance are essential.
- If stabilisation or horizon lock is accidentally left on at export, the static rig mask and the camera-to-BLK2GO extrinsic both become invalid. This is easy to miss because SfM still succeeds.
- Rolling shutter (X5 about 21 ms readout) during fast yaw turns distorts both lenses differently. Keep turns slow; 3DGUT trainers can model rolling shutter if needed.
- Under canopy, light is low, so a fast shutter forces high ISO. Noise reduces SIFT repeatability; in tropical forests, lens fogging and humidity add to this.
- On Windows: pycolmap has no CUDA wheels, so any pycolmap-based extraction or matching runs on the CPU and is slow. Whether the current Windows COLMAP release zips include CUDA could not be confirmed this session.
- Dataset size: 4-6k images at 1600-1920 px is about 30+ GB if cached raw in RAM, which needs trainers that stream from disk (Brush supports larger-than-RAM datasets). A 16 GB laptop GPU limits the Gaussian count rather than the number of images.
- FFmpeg v360 yaw/pitch sign and pixel-centre conventions may not match the extrinsics written into rig_config.json, giving a silently inconsistent rig. Validate with a synthetic check or by checking COLMAP reprojection error.
- Licences: SAM 3 uses the custom SAM License (bans ITAR/military uses); Ultralytics is AGPL-3.0; LichtFeld and the 360 plugin are GPL-3; LichtFeld prebuilt Windows binaries sit behind a paid portal (the source build is free); some 360-GS research repos include 3DGS-derived submodules whose licences were not checked.
- Sky and moving leaves in wind produce unstable features and blown highlights. Consider a 'sky' mask for SfM only.
- The web search budget ran out partway through this research. Some details (Blender pitfalls, OpenSfM/Metashape spherical, v360 pixel conventions, LichtFeld mask-mode flags, Grounded-SAM-2 licence) rest on background knowledge or secondary sources.

## FACT-CHECK: recommendation assessment

The recommendations largely hold. The core recipe checks out against primary sources: stabilisation-OFF export, a gnomonic reframe into a fixed virtual rig, COLMAP >=4.2 with rig constraints and per-image masks, ignore-in-loss masks in the trainer, and no Blender. Changes I would make:

(1) Fork pycolmap/panorama.py rather than 'reimplementing a custom reframer'. It already is a cv2.remap(INTER_LINEAR) reframer with exact rig JSON, uniqueness masks, rig_verification and EXIF prior propagation. The fork only needs three things: a user-mask input (remapped with INTER_NEAREST and ANDed with the uniqueness mask), a configurable layout (16 views), and timestamped frame naming.

(2) Windows GPU is no longer a blocker. Official colmap-x64-windows-cuda.zip exists for 4.2.1. Unofficial CUDA pycolmap 4.2.0 wheels (lyehe/build_gpu_colmap) also exist; use them or the colmap.exe CLI for extraction and matching.

(3) Drop the caveat that the global mapper may lack rig support. COLMAP 4.1 fixed refine_sensor_from_rig across all global-mapper stages and added global mapping to panorama_sfm, so test global_mapper as the fast default and incremental as the fallback. The lichtfeld-360-plugin README is stale on this point.

(4) Fix the factual slips. 3DGRUT is tag v1.1.0 (2026-06-10); 'v2.0' appears only in its README. insv-stitch's 21 ms rolling-shutter readout is an assumed model parameter, not a measurement. gsplat's simple_trainer already applies data['mask'] in the loss, so only the dataset loader needs patching. equilib rots is a dict. sharp-frames is MIT. Grounded-SAM-2 is Apache-2.0.

(5) Camera choice: recommend the X5 over the X6 unless the low-light gain is critical. All open tooling (MediaSDK, telemetry-parser, insv-stitch, insta360-rs stabilisation) is X5-only, and the gyro-based time-sync and rolling-shutter options depend on that tooling.

(6) For the 10x10 m first test, start leaner to iterate fast: about 0.4 m spacing, roughly 100 panos per loop, with COLMAP's 12-view layout. Move to 16 views and 0.25 m only if registration gaps appear. 4.8-6.4k images is heavy for a test.

(7) Treat the dual-fisheye/3DGUT route as research-grade for the web deliverable. Many standard viewers render 3DGUT-trained splats incorrectly (LichtFeld, Sep 2026). Train the delivery splat on pinhole views with standard rasterisation, or verify that the Three.js viewer handles 3DGUT output.

(8) Licensing for a Hexagon context: SAM 3 (SAM License) and AGPL YOLO are acceptable internally, but SAM 2.1 plus Grounded-SAM-2 (both Apache-2.0) is the clean default. ODGS's MIT label hides an Inria-derived simple-knn submodule. LichtFeld and the 360 plugin are GPL-3, fine for local use.

(9) In LichtFeld, use --mask-mode ignore explicitly. Alpha is used as a mask by default, and the default mode is none.

(10) Verify on a test clip that 360-mode .insv streams carry no baked in-camera rotation, since the manual says in-camera stabilisation 'cannot be manually disabled'.

Note: the WebSearch budget was exhausted at the start of this check, so verification relied on direct WebFetch of primary URLs (GitHub API and releases, official docs, LICENSE files, arXiv, vendor manuals). A few items remain unverified: the X5 5.7K60 mode, Blender's AgX default and 1.5 px filter width, Brush larger-than-RAM support, the simple-knn fork licence, and the 4.1 pose-prior rig fix quote.
