# gap: blk2go-trajectory

## Summary

Bottom line: Leica publishes no column-level spec for any BLK2GO trajectory CSV (BLK Live, Cyclone FIELD 360). Every public source only says that the trajectory 'can be exported to .csv'. The useful finds are elsewhere. (1) Cyclone 3DR (2024.1 and later) has a documented script class, STrajectory, that exposes full 6-DOF poses with timestamps for trajectories imported from LGSx. Its methods are GetNumberOfPoses, GetPoseInfo(index) which returns an SMatrix pose and a Timestamp, EstimatePose(timestamp) which interpolates, GetTimestampRange, LinkToCloud and Save(filePath) to CSV. This is the most reliable route to orientation over time with the user's licences. The 3DR GUI only exports trajectories to .lgsx; 'Polyline from trajectory' keeps geometry only. (2) Cyclone REGISTER 360 PLUS can export WayPoint panorama poses. In Report > Publish Options > Pano images, the CSV holds Setup poses and the TXT holds pano-image poses. Each pose is position x,y,z in metres plus a quaternion w,x,y,z. The 2026.0/2026.1 release notes fix quaternion-order bugs in these files 'for mobile and static data', which confirms they cover BLK kinematic data. WayPoints can be added anywhere along the walk with the Track Editor (distance or time slider). The minimum interval at import is 1 m, and walks with more than 100 WayPoints work from 2026.0.0. The three panoramic cameras capture about once per second. (3) 'Register360.exe -b2g2trajectory <b2g dir> <export dir>' (options recimage, interval=n, geotag-waypoints) and the GUI 'E57 Separate Setups' export with WayPoints both need a Cyclone WORKFLOW licence (the renamed PUBLISHER Pro). The CLI is not available in the BLK Edition. The E57 holds the main cloud, the trajectory as a second point cloud with 'normal calculations per point', and pano image poses. Leica's published writer code fills imageHeader.pose from e57CameraToPano as a quaternion (w,x,y,z) plus translation. Under the E57 standard, that pose is the camera frame expressed in the file-level frame, i.e. camera-to-world. That code also sets acquisitionDateTime with SetCurrentGPSTime(), so image timestamps in that E57 are probably the export time, not the capture time. Do not use them for sync. The docs do not say whether the trajectory point cloud has per-point timeStamp fields.

Timestamp hypothesis: the evidence strongly supports it. The BLK2GO User Manual v0.9 (Leica, 2019) gives Mirror rotation 100 Hz, Base rotation 2.5 Hz, PRF 1.64 MHz and a maximum scan rate of 410,000 pts/s; the spec sheet says 420,000 pts/s. xyHt quotes Hexagon's CTO: '100Hz on the fast axis'. With 8 ns ticks (125 MHz): 1,250,000 ticks = exactly 10 ms, one mirror revolution at 100 Hz. The 296-tick minimum step = 2.37 us (422 kHz). The mean step at 410 kpts/s would be about 305 ticks = 4 x 76 ticks, and 125 MHz/76 = 1.645 MHz, matching the stated PRF. The range 4.09e10 to 1.09e11 ticks = 327 to 872 s, a 545 s (about 9.1 min) span, which fits a battery limit of 45-50 min. Other units fail. Nanoseconds give a 1.25 ms (800 Hz) sweep and a 3.4 MHz minimum step, above the PRF. 320 ns ticks would match the 2.5 Hz base period, but give a 6 h span and 95 us steps. No Leica document names the unit. 3DR 2025.1 imports LAS GPS time 'as timestamps' and exports a timestamps attribute to LAS/E57, so the sample's gps_time is most likely the raw LGSx/device time copied through. Whether the zero point is device boot or scan start is unknown. Whether REGISTER 360 LAS/E57 exports carry the same per-point time is unknown.

Same clock for trajectory and points: no source says so for the BLK Live or FIELD 360 CSVs. 3DR's STrajectory.LinkToCloud and EstimatePose(timestamp) suggest that, inside 3DR, trajectory and cloud timestamps share one time base. This is an inference with medium-low confidence. Check it by comparing GetTimestampRange() with the cloud's timestamp range.

Reference point and body axes: not documented anywhere public. The trajectory origin is probably the LiDAR/IMU origin in the head (background, low confidence). The plan should estimate the Insta360-to-BLK2GO extrinsic from data (hand-eye or trajectory alignment) rather than rely on a published lever arm.

Licence: no public description of the 'TLS Software Demo / Eval. / EPP' bundle was found. The web search budget ran out before 'EPP' could be researched further. Check WORKFLOW empirically: run the -b2g2trajectory CLI, or do a GUI E57 export with Separate Setups and see whether WayPoints and rectified images are included. Also look at the activated products in Leica CLM (Client License Manager).

What this means for the plan: drop any dependence on the BLK Live/FIELD 360 CSV until a real export has been inspected. The primary route is: REGISTER 360 PLUS > publish LGSx > 3DR > STrajectory script that dumps t plus a 4x4 matrix per pose. Fallbacks: REGISTER 360 Pano-images TXT poses at densified WayPoints, and b2g2trajectory E57 if WORKFLOW is present. Treat per-point time as ticks/125e6 seconds, after the verification tests in recommendations. The two devices share no clock, so sync must be motion-based: SfM camera trajectory against BLK2GO trajectory, or Insta360 gyro against BLK2GO angular rate. A deliberate shake or tap event at start and end makes this easier.

## Plan changes

- Pipeline: add a 'BLK2GO pose extraction' stage. REGISTER 360 PLUS publishes LGSx, then a 3DR JavaScript runs STrajectory.GetPoseInfo/Save and writes trajectory_poses.csv (t, 4x4). Fallback parsers: REGISTER 360 Pano-images TXT (x,y,z,qw,qx,qy,qz) and b2g2trajectory E57 (pye57: trajectory cloud plus image poses).
- Pipeline: add a 'timestamp sanity' step for every LAS/E57 from 3DR: sort by gps_time, histogram the steps, detect the 10 ms sweep and 0.4 s base periods, and convert ticks to seconds (t_s = gps_time/125e6) only after the checks pass. Store the result as a new field; never overwrite the original.
- Pipeline: when trajectory and cloud times are proven compatible, compute the sensor position per point by interpolating the trajectory at each point's time. Use it for ray-based ground and free-space detection (navigation limits) and for moving-object filtering.
- Capture protocol: full-density firmware setting; a static start and stop on the base plate; a sharp shake or tap sync event at the start and end, visible to both the Insta360 gyro and the BLK2GO trajectory; note the wall-clock times. Optionally long-press for on-demand panos at marked targets.
- Capture protocol: in REGISTER 360, set the WayPoint interval to 1 m and add WayPoints with the Track Editor where denser orientation samples are needed.
- Phases: phase 1 (Swedish 10x10 m loop) uses spatial alignment plus motion-based time sync. Phase 2 adds time-based per-point fusion only after same-clock verification.
- Tools: add Cyclone 3DR scripting (JavaScript) to the toolchain. Use pye57/libE57Format to read the E57 trajectory and image poses. Mark the BLK Live/FIELD 360 CSV as 'unknown format: inspect first export'.

## Recommendations

- **Make 'REGISTER 360 PLUS > publish LGSx > Cyclone 3DR > STrajectory script' the primary way to get BLK2GO 6-DOF poses with timestamps. Loop GetPoseInfo(i) over GetNumberOfPoses() and write t plus the 16 matrix values per pose. Also call Save() once to see Leica's own CSV layout.** — It is the only documented route that gives orientation plus a timestamp per pose. The user has PLUS and 3DR, and it does not need WORKFLOW. _Alt:_ REGISTER 360 Pano images TXT (positions plus w,x,y,z quaternions at WayPoints, densified with the Track Editor); b2g2trajectory E57 if WORKFLOW is active; BLK Live/FIELD 360 CSV once inspected.
- **Before building on 'gps_time = ticks/125e6 s', run three checks on the sample. (a) Histogram of time steps inside contiguous runs: expect a peak near 300-310 ticks at full density. (b) A 1,250,000-tick (10 ms) sweep period, plus a 50,000,000-tick (0.4 s) period in the sweep-plane azimuth from the 2.5 Hz base rotation. (c) The total span against the walk duration in REGISTER 360 Properties.** — The 125 MHz hypothesis is strongly consistent with the manual's 100 Hz mirror and 1.64 MHz PRF, but no Leica document states it. Check (b) tests it independently. _Alt:_ Ask the BLK team directly through Hexagon contacts.
- **Treat per-point time and trajectory time as possibly different clocks or units until proven otherwise. In 3DR, compare STrajectory.GetTimestampRange() with the cloud's timestamp range. Find the offset and scale by matching sensor positions: each 10 ms sweep plane passes through the sensor, so its position can be checked against the trajectory.** — Same-clock behaviour is undocumented. Getting it wrong would corrupt ray-based free-space/ground logic and any time-based fusion. _Alt:_ Use only spatial alignment (no time fusion) for the first Swedish test.
- **Do not use E57 image acquisitionDateTime or REGISTER 360 export metadata for sync. Plan motion-based sync between the BLK2GO and the Insta360: SfM camera trajectory vs BLK2GO trajectory with a time-offset search, or Insta360 gyro vs BLK2GO angular rate from the 3DR poses. Add a deliberate sharp shake or tap at the start and end of each walk.** — The writer code stamps images with the current GPS time at export. The two devices share no clock. _Alt:_ Long-press on-demand pano or short-press detail image (GeoTag) as a manual event marker, if its time can be read in the same time base.
- **Estimate the Insta360-to-BLK2GO extrinsic (lever arm and rotation) from data rather than from a Leica-published reference point.** — No public source defines the BLK2GO trajectory origin or body axes. _Alt:_ Ask Leica for the trajectory reference frame definition, or measure it with a static calibration capture.
- **Check whether WORKFLOW is active: try 'Register360.exe -b2g2trajectory' on a B2G, or a GUI E57 export with Separate Setups, and see whether WayPoints and rectified images appear. Also check the activated products in CLM.** — What the Demo/Eval/EPP licence includes is unknown, and both E57 trajectory routes depend on WORKFLOW. _Alt:_ Ask the Leica/Luciad contacts what the EPP bundle includes.
- **Record the firmware density setting (full/medium/low) for each capture and use full density for test walks.** — Medium and low density filter points on the device. This changes timestamp statistics and point density near the ground. _Alt:_ None needed.

## Key numbers

- BLK2GO mirror (fast-axis) rotation: 100 Hz (10 ms per revolution) (BLK2GO User Manual v0.9 sec. 1.6.2; xyHt interview)
- BLK2GO base (slow-axis) rotation: 2.5 Hz (0.4 s period) (BLK2GO User Manual v0.9 sec. 1.6.2)
- Laser pulse repetition frequency: 1.64 MHz (BLK2GO User Manual v0.9 sec. 1.6.2)
- Max scan rate: 410,000 pts/s (manual) / 420,000 pts/s (spec sheet) (BLK2GO User Manual v0.9 sec. 7.3; BLK2GO spec sheet)
- Hypothesised tick period: 8 ns (125 MHz). 1,250,000 ticks = 10.000 ms; 296 ticks = 2.368 us; about 305 ticks = 2.44 us at 410 kHz; 50,000,000 ticks = 0.4 s base period (Derived from sample statistics and the manual)
- Sample gps_time range converted at 8 ns: 327 s to 872 s; span about 545 s (about 9.1 min) (Derived)
- Panoramic image capture rate: about 1 per second (3 global-shutter cameras, 1080x1440 each, 100x135 deg) (RCDOCS BLK2GO Support; User Manual sec. 7.1)
- Detail camera: 3040x4056 px, 90x120 deg, rolling shutter (BLK2GO User Manual v0.9 sec. 7.1)
- Minimum WayPoint interval at import: 1 m (more can be added in the Track Editor; limit of 100 per walk lifted in 2026.0.0) (RCDOCS BLK2GO Support; REGISTER 360 2026.0.0 release notes)
- Pano pose file format: position x,y,z (m) + quaternion w,x,y,z; CSV = Setup poses, TXT = pano image poses (RCDOCS option-to-publish-pano-images)
- E57 pinhole pixel size in Leica writer: 6.0e-6 m (RCDOCS B2G to E57 code listing)
- 3DR STrajectory availability: Script docs 2024.1, 2025.0, 2026.1 (not 2023.1) (cyclone3dr.leica-geosystems.com help)
- BLK Live current version: 3.0.2 (2025-07-22); BLK2GO support and trajectory .csv export listed from 2.0.0 (2023-12-13) (Apple App Store BLK Live page)

- Whether the E57 trajectory point cloud from b2g2trajectory or the GUI export carries per-point timeStamp fields, and what its 'normals' encode (heading, up vector?).
- Whether REGISTER 360 PLUS LAS or E57 exports of BLK2GO clouds carry per-point time, and in which units.
- The zero point of the 125 MHz tick counter (device boot vs scan start), and whether trajectory and point times use the same counter.
- The physical origin and body axes of the BLK2GO trajectory (LiDAR centre, IMU, or base plate).
- The column order and headers of the REGISTER 360 Pano-images CSV/TXT pose files (only 'x,y,z' and 'w,x,y,z' are documented). Whether the files contain WayPoint times.
- What the 'TLS Software Demo / Eval. / EPP' licence includes (WORKFLOW? anything else). 'EPP' was not researched because the search budget ran out.
- Official confirmation of the 125 MHz tick unit. Only arithmetic consistency with the manual's 100 Hz mirror, 2.5 Hz base and 1.64 MHz PRF supports it.
