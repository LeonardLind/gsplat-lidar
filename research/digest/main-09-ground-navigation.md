# ground-navigation

## Summary

STATE OF THE ART AND WHAT IT MEANS FOR THIS PROJECT (as of 2026-10-06). Note: the shared web-search budget ran out partway through. Later facts were checked by fetching primary pages directly (GitHub, npm/PyPI registries, PDAL/GDAL docs). A few accuracy figures come from background knowledge and are marked low confidence.

1) GROUND FILTERING. Handheld SLAM LiDAR under a canopy gives very dense ground near the walked path. Ground density drops quickly with distance because stems block the view and the beam hits the ground at a low angle. Classic airborne (ALS) filters work if they are rescaled from ALS cell sizes (1 m or more) to 0.1-0.5 m.
- Main tool: PDAL 2.10.2 (released 2026-06-12; conda-forge win-64, BSD-3) provides filters.csf, filters.smrf, filters.pmf, plus noise pre-filters (filters.elm, filters.outlier), filters.delaunay + filters.faceraster (TIN to raster), writers.gdal (with IDW hole fill) and filters.hag_*.
- PDAL defaults are ALS-scale: CSF resolution 1.0 m / threshold 0.5 m; SMRF cell 1.0 m / window 18 m. They must be scaled down.
- Pitfall: all three ground filters default to returns="last, only". SLAM LAS exports often carry NumberOfReturns=0, which triggers "No returns to process" or silently filters nothing. Fix with filters.assign (set the return fields to 1) before the filter.
- On Windows use conda-forge `pdal` + `python-pdal` (3.5.5). The pip `pdal` 3.5.5 is source-only on Windows, and `pip install python-pdal` installs a dependency-confusion placeholder.
- Standalone CSF: `cloth-simulation-filter` 1.1.7 (2025-08-13, Apache-2.0). Windows wheels exist only for cp39-cp312, so pin Python 3.12. The API field is misspelled `interations`.
- Evidence: CSF beat other filters on TLS data (Kappa 0.86) but is sensitive to time_step. Forest handheld studies used cloth resolution 0.5 m, threshold 0.1 m, 500 iterations.
- lidR (R, GPL-3; 4.3.3 on 2026-09-15) added progressive TIN densification (ptd()) in 4.3.0. Its book says PTD "outperforms the other methods in all contexts" and was 8x faster than CSF on its mountain example. This is a good cross-check tool, but it adds an R dependency.
- RANSAC plane fitting is inadequate for a forest floor. Use it only as a local sanity check.
- Deep learning: ForAINet (BSD-3), ForestFormer3D (ICCV 2025, CC BY-NC 4.0, so non-commercial only; this matters at Hexagon), SegmentAnyTree V1 (MIT, instance segmentation only, Linux-only) and SegmentAnyTreeV2 (arXiv 2026-06, ground IoU 98.9%; code and weights promised "upon acceptance") all predict ground/wood/leaf. They need Linux-style stacks (MinkowskiEngine/spconv/Docker), so on Windows they run through WSL2. They are overkill for a 10x10 m boreal test but are an option for dense tropical understory.
- FSCT (GPL-3) outputs a terrain class and DTM plus stems/cylinders. It is unmaintained since 2022-09 and suggests 128 GB RAM.

2) NAVIGATION GEOMETRY. Build the DTM at 5 cm (test) or 10 cm (large sites), crop it to where ground points actually support it, and fill holes (writers.gdal window_size, or gdal_fillnodata with -md/-si; GDAL 3.9+ adds -interp nearest).
- Better quality: Delaunay over the ground points, then faceraster with max_triangle_edge_length so the filter does not interpolate across large gaps.
- Export a float32 GeoTIFF as the master copy. For the web, ship raw float32/uint16 tiles plus a JSON header, or the GeoTIFF read with geotiff.js (MIT, 3.0.5).
- Collision/visual ground mesh: max-error TIN via delatin (JS, ISC), pydelatin/hmm (MIT) or fast-simplification (MIT, Windows wheels), exported to glTF.
- Obstacles in a forest are not "all LiDAR points": foliage and shrubs should be passable. The obstacles that matter are stems (and later boulders/logs). Extract them by height-above-ground slicing (filters.hag_dem/hag_delaunay), then DBSCAN, then RANSAC circle fit per slice, then link slices into leaning cylinders. 3DFin/dendromatics (GPL-3; Windows exe, pip, CloudCompare and QGIS plugins; CSF-based) does this robustly. TreeQSM (GPL-3, MATLAB) and 3D Forest (GPL-3) are heavier alternatives.
- A voxel occupancy grid plus a Euclidean distance field (scipy distance_transform_edt) is the general "solid surface" representation. It costs 1 byte per voxel (8 MB for 20x20x20 m at 10 cm), so it is optional or sparse rather than the default.

3) VIEWER-SIDE COLLISION. Treat collision as a constraint step run after the camera controls update: `controls.update(camera)` (Spark 2.3.1 SparkControls/FpsMovement/PointerControls; three.js PointerLock; nipplejs 1.0.4 for a phone joystick), then the solver.
- Heightfield clamp: O(1) bilinear sample. Walk mode sets eye height ~1.6 m with smoothing and a slope/step limit. Fly mode enforces a minimum clearance.
- Stems: analytic 2D circle-vs-circle push-out through a spatial hash. Effectively free even on phones.
- Arbitrary surfaces (user-drawn walls, rocks, logs): capsule shapecast against a merged collision mesh using three-mesh-bvh (MIT, 0.9.15, 2026-09-09; characterMovement example). A built-in alternative is the three.js Octree + Capsule from the games_fps example.
- Optional extras: a Recast navmesh (recast-navigation-js MIT 0.43.1, with TileCache cylinder obstacles and findClosestPoint) and Rapier's KinematicCharacterController (Apache-2.0, 0.21.0; the rapier.js repo was archived 2026-07 and moved into the main rapier repo).
- Do not collide against the splat: Spark's raycast is a WASM loop over all splats, and its docs warn against calling it per frame. Collide against LiDAR-derived geometry in the shared metric frame.
- Scene bounds = region where the DTM is supported ∩ a buffer around the capture path (where splat quality is good), plus z limits.

4) RECOMMENDATION. For the 10x10 m test: PDAL CSF (resolution 0.15-0.25 m, rigidness 2, threshold 0.08-0.15 m) after downsampling and ELM/outlier noise removal, cross-checked with SMRF. Then a 5 cm DTM via TIN rasterization, a hole-fill, and a support mask. Then stems as a cylinder list, bounds as a polygon, and user boundaries as JSON. Viewer: heightfield clamp + analytic stems + three-mesh-bvh for walls/meshes; walk and fly modes with different constraints.
To scale: tile ground filtering with buffers, use 10 cm quantized DTM tiles, a spatial hash for stems, per-tile BVH/navmesh, footprint polygons for buttress roots, and optional deep-learning ground segmentation (license-checked) for tropical sites.

## Recommendations

- **Ground-filter pipeline for the 10x10 m test (PDAL from conda-forge, Python 3.12 environment): readers.las/readers.e57 → filters.crop (loop bbox + ~8-10 m buffer) → filters.assign (ReturnNumber=1, NumberOfReturns=1 when 0/missing) → filters.voxelcenternearestneighbor (cell 0.02-0.03 m) → filters.outlier (statistical, mean_k ~12, multiplier ~2.5) → filters.elm (cell ~0.5-1.0 m, threshold ~0.3-0.5 m) → filters.expression drop class 7 → filters.csf (resolution 0.15-0.25, rigidness 2, threshold 0.08-0.15, hdiff 0.3, step 0.65, smooth true, iterations 500). Run filters.smrf (cell 0.25, window 4-6 m, slope 0.2-0.4, threshold 0.2, scalar 1.25) as a cross-check and diff the two ground sets in CloudCompare cross-sections.** — CSF has the best TLS/handheld evidence and is native to PDAL, the Python package, CloudCompare and 3DFin. The PDAL defaults are ALS-scale (1 m cells, 0.5 m threshold). The returns pitfall and low-noise spikes are the two most likely failure modes on SLAM LAS exports. Everything listed is BSD/Apache and runs on Windows. _Alternatives:_ pip cloth-simulation-filter 1.1.7 directly on numpy arrays (Python ≤3.12 on Windows). lidR 4.3.x ptd() in R as a third opinion. Cyclone 3DR ground extraction if the license is at hand (not verified; must not be a hard dependency).
- **DTM: thin ground points to ~3-5 cm, then filters.delaunay + filters.faceraster (resolution 0.05 m for the test, max_triangle_edge_length ~1.0-1.5 m) → GeoTIFF float32 (master copy, local metric frame). Then gdal_fillnodata (-md 20-40 px, -si 1) on interior holes only, and a 1-2 cell Gaussian smooth for walk-mode comfort. Also write a 'support' raster (ground points per cell or distance to nearest ground point) and use it to define the navigable/trustworthy area.** — TIN interpolation preserves microrelief and refuses to bridge large occlusions. The support mask prevents walking into extrapolated terrain at the 25 m-range fringe of the cloud. 5 cm cells keep a 30x30 m area at ~1.4 MB float32. _Alternatives:_ writers.gdal output_type idw or min with window_size 3-10 for faster coarse DTMs. FSCT's terrain DTM (GPL-3) as a deep-learning comparison.
- **Obstacles: compute HeightAboveGround (filters.hag_dem using the DTM, or hag_delaunay). Take 3-4 thin slices (e.g. 0.5-0.8, 1.1-1.5, 1.8-2.2, 2.6-3.0 m), then DBSCAN in XY (eps 0.05-0.08 m, min_samples ~15), then RANSAC circle fit (skimage CircleModel; residual ≤1-2 cm; radius 0.03-0.6 m; arc coverage >120°). Link section centres into leaning cylinders and export stems.json [{id, base xyz, top xyz, radius(z)}]. Validate against 3DFin (Windows exe/pip, GPL-3) on the same cloud.** — In forests, 'solid' for navigation means stems (and later boulders/logs), not foliage or shrubs. Analytic cylinders are tiny, exact, and make collision on phones essentially free. The custom code uses only BSD/MIT libraries, and 3DFin gives an independent check without coupling GPL code into the project. _Alternatives:_ 3DFin output used directly. FSCT cylinders. TreeQSM (MATLAB) for full branch QSMs, which is unnecessary for collision.
- **Viewer collision architecture (Three.js + Spark): run the controls update (SparkControls / PointerLock / nipplejs joystick on phones), then a constraint solver with substeps so per-step motion stays below the body radius. Solver order: (1) scene-bounds polygon + z-range clamp. (2) Walk mode: y = smoothedDTM(x,z) + 1.6 m eye height; reject steps above ~0.4 m or slopes above ~35-40°; 2D circle push-out against stems (stem r + body r 0.25-0.3 m) through a spatial hash; segment push-out against user-drawn walls. (3) Fly mode: y ≥ DTM + 0.3 m (plus registration error margin); sphere/capsule vs stems and walls; optional three-mesh-bvh capsule shapecast against a merged collision mesh (DTM TIN + rocks/logs + wall quads); foliage passable; optional max altitude. Never raycast the splat per frame.** — The heightfield clamp is O(1) and the stem tests are O(k). three-mesh-bvh handles arbitrary triangles cheaply (500 rays vs 80k polys at 60 fps on its demo). Spark's splat raycast is documented as too slow for per-frame use. Splat rendering, not collision, will dominate phone frame time. _Alternatives:_ three.js Octree + Capsule (games_fps) instead of three-mesh-bvh. Rapier KinematicCharacterController (Apache-2.0) with heightfield/trimesh colliders. Recast navmesh (recast-navigation-js, MIT) with TileCache cylinder obstacles for click-to-walk and pathfinding.
- **User-defined boundaries: let users draw polylines on the ground (raycast the DTM TIN with three-mesh-bvh acceleratedRaycast), extrude them to vertical walls (e.g. 3 m, or infinite for walk mode), and optionally draw an 'allowed region' polygon. Store boundaries as JSON in the shared scene frame and ship them with the scene; keep localStorage only for drafts. Walk mode uses 2D segment-vs-circle tests; fly mode adds the wall quads to the collision BVH.** — This is simple, deterministic, cheap on phones, and independent of Luciad. It also lets curators mask regions where the splat or DTM is poor. _Alternatives:_ Box no-fly volumes. Automatic bounds from the capture trajectory buffer only.
- **Scene bounding volume = (DTM support mask) ∩ (buffer of 2-4 m around the SfM camera path and/or BLK2GO trajectory) for walk mode, plus a wider buffer and a z range (ground to canopy top + margin) for fly mode.** — Splat quality and LiDAR ground support both degrade away from the capture path. Bounding by the capture path keeps viewers where the fused scene looks good. _Alternatives:_ A plain AABB of the cropped LiDAR. A convex hull of the camera positions.
- **Asset formats: dtm.tif (float32 GeoTIFF, master copy) plus web tiles (raw Float32 or Uint16-mm with a JSON header, or GeoTIFF read with geotiff.js). Collision ground mesh: delatin TIN (maxError ~2 cm), built client-side or as a meshopt-compressed glb. Also stems.json, bounds.json, boundaries.json, and optional sdf.bin (uint8, 10 cm, solid classes only). Use one local origin and a Z-up to Y-up conversion shared with the splat registration transform.** — All small and permissively licensed (MIT/ISC). Float32 precision and frame consistency are the main correctness risks when fusing LiDAR and splat at metric scale. _Alternatives:_ glTF ground mesh only, with the heightfield sampled from mesh raycasts (simpler, slower). 3D Tiles for very large terrain.
- **Scaling to larger and denser (tropical) forests: tile ground filtering (e.g. 50x50 m tiles with 5-10 m buffers via filters.splitter or a lidR catalog). Raise CSF cloth resolution to 0.3-0.5 m and expect bigger holes, so lean more on the support mask and interior-only hole filling. Use a 10 cm DTM in 256x256 quantized tiles streamed by camera position. Index stems in a grid spatial hash (thousands of stems per ha are fine). Model buttress roots as footprint polygons from low-slice alpha shapes instead of circles. Build a BVH or navmesh per tile (recast tiled navmesh). Evaluate deep-learning ground/wood/leaf segmentation in WSL2: ForAINet (BSD-3), or SegmentAnyTreeV2 once code and weights are released. Use ForestFormer3D (CC BY-NC) only for non-commercial benchmarking.** — Dense understory breaks morphological and cloth filters (vegetation gets absorbed into ground), and the occluded ground needs semantic help. Collision cost scales with local density only if spatially indexed. License terms matter for a Hexagon employee. _Alternatives:_ FSCT (GPL-3, unmaintained since 2022). lidR ptd() in R per tile.
- **Keep Luciad optional: export the navigation data in neutral formats (GeoTIFF DTM, GeoJSON/JSON stems and boundaries in a documented CRS/local frame) so a LuciadRIA client could reimplement the clamp and collision in its own controller later.** — No LuciadRIA navigation-constraint documentation could be verified (dev.luciad.com pages returned 404 and the search budget was exhausted). The web viewer must not depend on it. _Alternatives:_ Skip Luciad navigation constraints entirely and use Luciad only for visualization of LiDAR/splat.

## Load-bearing findings (claim + sources)

- [high] PDAL's ground filters (csf, smrf, pmf) default to ALS-scale parameters and to returns='last, only'; they must be rescaled for handheld forest data. — https://pdal.io/en/stable/stages/filters.csf.html https://pdal.io/en/stable/stages/filters.smrf.html https://pdal.io/en/stable/stages/filters.pmf.html
- [medium] Pitfall: SLAM/TLS LAS files with NumberOfReturns=0 (or missing) make SMRF/PMF fail with 'No returns to process'; the workaround is filters.assign to set NumberOfReturns/ReturnNumber to 1 before ground filtering. — https://lists.osgeo.org/pipermail/pdal/2019-January/001705.html https://github.com/PDAL/PDAL/issues/2634 https://pdal.io/en/stable/stages/filters.csf.html
- [high] On Windows, install PDAL from conda-forge. pip 'pdal' 3.5.5 ships no Windows wheel, and 'python-pdal' on PyPI is a dependency-confusion placeholder. — https://github.com/PDAL/PDAL/releases https://anaconda.org/conda-forge/pdal https://anaconda.org/conda-forge/python-pdal
- [medium] CSF is the most-used and best-evidenced ground filter for TLS/handheld forest data, but it is parameter-sensitive and tends to absorb dense low vegetation into ground. — https://www.researchgate.net/publication/363881229_Comparison_of_Ground_Point_Filtering_Algorithms_for_High-Density_Point_Clouds_Collected_by_Terrestrial_LiDAR https://www.maxapress.com/article/doi/10.48130/smartfor-0026-0008 https://pmc.ncbi.nlm.nih.gov/articles/PMC12473678/
- [high] DTM creation and hole filling can be done entirely with PDAL + GDAL; TIN-based rasterization with a max edge length avoids interpolating across occluded gaps. — https://pdal.io/en/stable/stages/filters.faceraster.html https://pdal.io/en/stable/stages/writers.gdal.html https://gdal.org/en/stable/programs/gdal_fillnodata.html
- [high] Tree stems are the right 'solid obstacle' primitive in forests; 3DFin/dendromatics (GPL-3) implements CSF normalization, slice-based stem detection, DBSCAN and section circle fitting, and runs natively on Windows. — https://github.com/3DFin/3DFin https://github.com/3DFin/3DFin/releases https://github.com/3DFin/dendromatics
- [high] three-mesh-bvh (MIT, 0.9.15, 2026-09-09) is the standard way to do capsule-vs-mesh collision in Three.js; it also offers PointsBVH, closestPointToPoint, serialization of prebuilt BVHs and GPU SDF generation. — https://github.com/gkjohnson/three-mesh-bvh https://github.com/gkjohnson/three-mesh-bvh/releases https://registry.npmjs.org/three-mesh-bvh/latest
- [high] Do not use the Gaussian splat itself for collision: Spark's SplatMesh raycast is a synchronous WASM loop over all splats and is documented as unsuitable for per-frame use. — https://sparkjs.dev/docs/splat-mesh/ https://github.com/sparkjsdev/spark/releases https://registry.npmjs.org/@sparkjsdev/spark/latest

## risks

- Cyclone LAS export may carry NumberOfReturns/ReturnNumber = 0, which makes PDAL SMRF/PMF/CSF fail or process nothing until filters.assign fixes it.
- Dense low vegetation (Vaccinium, ferns; much worse in tropical understory) gets absorbed into the CSF ground, biasing the DTM upward by shrub height. For eye-height clamping, ±10-20 cm is tolerable, but it shows up as the camera floating relative to the splat floor.
- Low outliers or multipath points below the ground create CSF spikes. ELM/outlier pre-filtering is required, and the ALS defaults (ELM cell 10 m) are wrong for this data.
- BLK2GO's 25 m range yields a large, sparsely supported ground fringe. Without a support mask the viewer lets users walk on extrapolated terrain.
- The operator's legs or moving people may appear as near-path non-ground points and be detected as false stems or obstacles. Unverified whether Cyclone removes them; filter by cluster shape and verticality.
- Treating all LiDAR points (foliage, twigs) as solid makes fly or walk navigation impossible in dense forest. Collision must be restricted to ground + stems + explicit obstacles.
- Splat vs LiDAR registration error means the splat ground can sit a few cm above or below the LiDAR DTM. Set fly clearance ≥ registration RMSE + margin.
- Float32 precision loss if georeferenced coordinates (e.g. SWEREF99 TM) are used without a local origin.
- Tunneling through thin stems at high fly speed (Spark Caps Lock = 10x speed) unless substepping or swept tests are used.
- License traps: ForestFormer3D is CC BY-NC 4.0 (non-commercial). FSCT, 3DFin, dendromatics, lidR, lasR, TreeQSM and 3D Forest are GPL-3: fine as standalone tools, but do not link them into distributed proprietary code.
- Deep-learning forest models (ForAINet, SegmentAnyTree, ForestFormer3D) are tested on Linux; on Windows 11 they need WSL2/Docker with CUDA. 16 GB of laptop VRAM may force smaller inference tiles.
- The CSF PyPI package has no Windows wheels for Python 3.13+, which could constrain the shared Python environment.
- FSCT is unmaintained (last commit 2022-09-17) and memory-hungry (128 GB RAM suggested).
- The web search budget was exhausted mid-research. No primary source was found giving handheld under-canopy DTM RMSE, and LuciadRIA navigation APIs could not be verified.

## FACT-CHECK: recommendation assessment

The core recommendations hold. They are: PDAL from conda-forge; scaled-down CSF cross-checked with SMRF; ELM/outlier pre-cleaning; TIN DTM via delaunay + faceraster with a max edge length; a support mask and interior-only hole fill; stems as analytic cylinders from HAG slices; a viewer constraint step after the Spark controls update (heightfield clamp, circle push-out against stems, optional three-mesh-bvh capsule against walls and meshes); and never colliding against the splat. Every version, licence and default I checked in that chain is accurate. Spark's docs confirm there is no constraint or collision API and warn against per-frame splat raycasts, so the custom post-update solver is the right design.

Changes I would make:
1. Drop the NumberOfReturns framing. It is stale (PDAL 1.8, 2019). PDAL 2.x proceeds with a warning when both return fields are all zero and errors only on mixed zeros. Keep `pdal info --stats`, and add filters.assign only if the fields are partly populated.
2. Do not pin Python 3.12 for CSF. Use PDAL's filters.csf, or csf-3dfin 2.0.1, which has win_amd64 wheels up to cp313. Python 3.13 is the ceiling if 3DFin/dendromatics share the environment.
3. Treat the CSF numbers (resolution 0.15-0.25 m, rigidness 2) as a starting point for a sweep, not a recommendation. A fine, soft cloth drops into occluded patches and drapes onto shrubs; in the inverted cloud, ground gaps let the cloth reach vegetation. On a mostly flat boreal moss/Vaccinium floor, also try rigidness 3 and resolution 0.3-0.5 m, then judge by cross-sections and the SMRF diff. This is my reasoning; no handheld-forest source tests it.
4. Re-rank the deep-learning options for handheld data. ForAINet was built for drone ULS and uses ground / low-vegetation / stem / branch classes, so there is a domain gap. ForestFormer3D (CC BY-NC) was validated on LAUTx, which is probably handheld data (medium confidence), but it cannot be used commercially. SegmentAnyTreeV2 has no code or weights yet. For tropical sites, plan on the CSF + support mask + manual boundaries route, and treat deep learning as an R&D experiment, not a pipeline dependency.
5. For stem slicing, use hag_dem against the hole-filled DTM rather than hag_delaunay. With allow_extrapolation=false, hag_delaunay sets HAG to 0 outside the ground extent, so fringe stems silently drop out of the slices.
6. Add PlayCanvas splat-transform and SuperSplat Viewer, both MIT. Splat-transform's voxel collision export (`--voxel-floor-fill`, `--voxel-carve 1.6,0.2`, `--collision-mesh`) gives a splat-derived ground and collision surface. Diff it against the LiDAR DTM to measure vertical splat/LiDAR misregistration, and use it as a fallback for Insta360-only areas. SuperSplat Viewer's walk mode, which takes a .glb collision mesh, can serve as a no-code baseline for the LiDAR-derived collision GLB. Keep the custom Three.js/Spark viewer for the LiDAR/splat toggle.
7. Update the stale or imprecise facts:
   - fast-simplification is at 0.2.0, with wheels up to cp314.
   - TreeLearn was last pushed 2026-02.
   - SciPy's EDT has no PyTorch-GPU backend.
   - The Cyclone REGISTER 360 export list does not include LAZ; convert with PDAL or laspy.
   - The CSF evidence base is a TLS hillslope study and a garden MLS study, not forest studies.
8. The LuciadRIA navigation APIs and handheld under-canopy DTM accuracy remain unverified, so the neutral-format hedge and a field check against RTK or tape points are still needed.

Caveat: the shared web-search budget ran out during this check. Verification was done by fetching primary pages directly (GitHub API, PyPI/npm/conda registries, PDAL/GDAL/SciPy docs, arXiv, Crossref/Semantic Scholar), so very recent third-party developments outside those sources may be missing.
